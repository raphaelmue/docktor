# Phase 05.1: Code Review Report

**Reviewed:** 2026-09-02T00:00:00Z
**Depth:** standard

## Summary

This phase's file set is dominated by defensive, well-commented stabilization work (schema-sync locking, backup/restore SSE broadcaster lifecycle, file-watcher `.env` tracking, stacks-dir path-mismatch guard) and the tests are unusually thorough about pinning prior regressions. Most of the code holds up well under adversarial reading.

One real correctness/data-integrity gap was found: `BackupService.initiateRestore()` never validates the stack's current status before transitioning it to `RESTORING`, unlike every other state-changing operation in the codebase (`initiateBackup`, `deployStack`, `stopStack`, `restartStack`, `updateImages`, `upgradeServiceImage` all call `assertTransition`/`guardTransition` first). This is a plausible restore-vs-concurrent-operation collision (BLOCKER).

The rest are quality/robustness findings: a client-side breadcrumb link that silently drops tab context because it uses the wrong URL shape, an application-layer function that bypasses the repository abstraction the project's own CLAUDE.md mandates, a Dockerfile that verifies checksums for the restic binary but not for the Docker CLI/Compose plugin it also ships with host-socket access, a hardcoded default Postgres password in the shipped `docker-compose.yml`, and a restore code path that silently continues with an empty env object instead of failing fast.

## Critical Issues

### CR-01: `initiateRestore()` never validates the stack's current status before transitioning to RESTORING

**File:** `server/src/application/backup-service.ts:311-340`
**Issue:**
`initiateBackup()` explicitly guards the transition before doing anything else:
```ts
async initiateBackup(stackId: string, trigger: BackupTrigger = "MANUAL"): Promise<{id: string}> {
    const stack = await this.stackRepo.findByIdOrThrow(stackId)
    assertTransition(stack.status, "BACKUP")
    ...
```
`initiateRestore()` — its documented mirror ("Mirrors initiateBackup/runBackup's split") — has no equivalent call:
```ts
async initiateRestore(stackId: string, snapshotId: string): Promise<{id: string}> {
    const stack = await this.stackRepo.findByIdOrThrow(stackId)

    const repoConfig = await this.getBackupRepoConfig()
    if (!repoConfig) {
        throw new BadRequestError(...)
    }

    const backup = await this.backupRepo.create({...})
    ensureBackupBroadcaster(backup.id)

    await this.writeStackStatus(stackId, {
        status: "RESTORING",
        previousStatus: stack.status,
    })

    return {id: backup.id}
}
```
There is no `assertTransition(stack.status, "RESTORE")` (or equivalent) anywhere in this method. Every other state-changing action in `StackService` and `BackupService.initiateBackup` validates the current status first; this one does not. Concretely, this means a restore can be triggered while the same stack is `DEPLOYING`, `BACKING_UP`, `UPDATING`, or already `RESTORING` — `writeStackStatus` will happily overwrite the status to `RESTORING` regardless, and `runRestoreProcess` will proceed to `docker.stop()` + `restic restore` + `docker.up()` against a stack that may have an unrelated operation actively mutating its files or containers at the same time. That is a concrete data-corruption / data-loss risk, not just a cosmetic status-log inconsistency.

The unit test suite (`server/test/unit/application/backup-service.test.ts`, `describe("initiateRestore()")`) does not cover this — it only asserts the happy path, the broadcaster registration, and the "no repo configured" rejection. There is no test proving a restore is rejected (or even queued/blocked) when the stack is mid-deploy or already backing up.

Note: `server/src/routes/backups.ts` (the HTTP route that calls `initiateRestore`) was not part of this review's required-reading set, so it is possible — but unconfirmed — that a route-level check exists. Per this project's own layering rules (CLAUDE.md: "Domain code is pure... Services never import route types"), the guarantee belongs in the service/domain layer regardless of what the route does, exactly as `initiateBackup` demonstrates.

**Fix:**
```ts
async initiateRestore(stackId: string, snapshotId: string): Promise<{id: string}> {
    const stack = await this.stackRepo.findByIdOrThrow(stackId)
    assertTransition(stack.status, "RESTORE") // add the missing guard, mirroring initiateBackup

    const repoConfig = await this.getBackupRepoConfig()
    ...
```
If `"RESTORE"` is not yet a modeled action in `domain/stack-status-machine.ts`, add it with an explicit allowed-from list (e.g. `RUNNING`, `STOPPED`, `ERROR`) rather than leaving the transition unguarded.

## Warnings

### WR-01: Stack-detail breadcrumb link uses a query string the router doesn't consume, silently dropping tab context

**File:** `client/src/routes/app/stacks/[id].tsx:176`
**Issue:**
```tsx
<Link to={`/stacks/${id}${activeTab !== 'overview' ? `?tab=${activeTab}` : ''}`}>{stack.displayName}</Link>
```
The registered route is `path="/stacks/:id/:tab?"` (`client/src/main.tsx:86-88`), a **path** segment, not a query parameter — and the rest of this same file navigates correctly via the path form: `navigate(\`/stacks/${id}/${v}\`)` (line 234) for tab switches. Clicking the stack-name breadcrumb while on any tab other than Overview (e.g. Compose, Environment, Logs, Backups) therefore navigates to `/stacks/${id}?tab=compose`, which the router resolves as `/stacks/:id` with `tab` undefined — i.e., it silently jumps back to the Overview tab instead of staying put. This directly contradicts the intent documented in `client/test/integration/stacks.spec.ts` ("Breadcrumb preserves tab context (04-CONTEXT locked decision)"), but that test only exercises the Overview-tab case (where the bug is invisible, since the link degenerates to the correct `/stacks/${id}` there), so the regression is unexercised by the current suite.
**Fix:**
```tsx
<Link to={`/stacks/${id}${activeTab !== 'overview' ? `/${activeTab}` : ''}`}>{stack.displayName}</Link>
```
and add a Playwright/unit test that clicks the breadcrumb from a non-Overview tab and asserts the tab is preserved.

### WR-02: `backupStackRepo.update` bypasses the repository layer and uses an unjustified `as` cast

**File:** `server/src/application/index.ts:33-39`
**Issue:**
```ts
const backupStackRepo: BackupStackRepo = {
    findByIdOrThrow: (id: string) => repo.findByIdOrThrow(id),
    update: async (id: string, data: Record<string, unknown>) => {
        const {prisma} = await import("../lib/db.js")
        await prisma.stack.update({
            where: {id},
            data: data as {status?: StackStatus; previousStatus?: StackStatus | null},
        })
    },
    ...
```
Two separate CLAUDE.md rules are violated here: (1) "Do not import Prisma client outside `repositories/` or `lib/database.ts`" / "Repositories are the only place that touches Prisma" — this is `application/`, and it reaches for Prisma directly instead of adding a method to `StackRepository`; (2) "No unchecked casts — `as SomeType` is only acceptable with a comment explaining why it is safe" — the `as {status?: ...; previousStatus?: ...}` cast has no such comment, and since it's just a compile-time assertion (not a runtime narrowing), any extra keys present on the caller's `data` object at runtime (e.g. from `writeStackStatus`'s `Record<string, unknown> & {status: StackStatus}` signature) are passed through to `prisma.stack.update` unchecked.
**Fix:** Add a proper `update()` method to `StackRepository` that accepts a narrow, explicit shape (e.g. `{status: StackStatus; previousStatus?: StackStatus | null}`), and have this adapter call that instead of reaching for the Prisma client directly.

### WR-03: Docker CLI / Compose plugin installed without checksum verification, unlike the restic binary in the same Dockerfile

**File:** `Dockerfile:67-73`
**Issue:** The restic-install stage goes out of its way to checksum-verify the downloaded binary and explains why: "important because this binary will run with access to the host Docker socket" (`Dockerfile:42-44`). The very next thing installed — the Docker CLI and Compose plugin, which run with the *same* host-socket access — is fetched with plain `curl -fsSL` and piped straight into `tar`/written directly to `/usr/local/lib/docker/cli-plugins/docker-compose`, with no `sha256sum -c` step:
```dockerfile
RUN curl -fsSL https://download.docker.com/linux/static/stable/x86_64/docker-27.5.1.tgz | \
    tar xz --strip-components=1 -C /usr/local/bin docker/docker && \
    mkdir -p /usr/local/lib/docker/cli-plugins && \
    curl -fsSL -o /usr/local/lib/docker/cli-plugins/docker-compose \
      https://github.com/docker/compose/releases/download/v2.33.1/docker-compose-linux-x86_64 && \
    chmod +x /usr/local/lib/docker/cli-plugins/docker-compose
```
This is an inconsistent application of the project's own stated security rationale — both binaries are equally security-sensitive (both directly drive the host Docker daemon).
**Fix:** Pin and verify checksums for both downloads the same way the restic stage does (Docker publishes a `.sha256` alongside static binaries; docker/compose release assets ship a checksums file too).

### WR-04: Hardcoded, weak default Postgres password shipped in `docker-compose.yml`

**File:** `docker-compose.yml:70-73`
**Issue:**
```yaml
environment:
  POSTGRES_USER: docktor
  POSTGRES_PASSWORD: docktor
  POSTGRES_DB: docktor
```
`docs/deployment.md` tells operators to "use the *same* password in `docker-compose.yml`'s `db.environment.POSTGRES_PASSWORD`" after changing `.env.local`'s `DATABASE_URL`, but the compose file itself ships a literal, guessable default (`docktor`) rather than a placeholder the operator is forced to notice/change (contrast with `.env.example`'s `CHANGE_ME_DB_PASSWORD` convention referenced in the same doc). An operator who follows only the three-step Quickstart in `README.md` (`cp .env.example .env.local && docker compose up -d`) without reading the "fill in the CHANGE_ME values" prose closely will end up running Postgres with a well-known default password. Exposure is currently limited (no `ports:` mapping on the `db` service, so it's only reachable from the `docktor` container over the compose network), but this is still a real weak-default-credential finding.
**Fix:** Either drive `POSTGRES_PASSWORD` from the same env var the app's `DATABASE_URL` uses (so there's a single source of truth and no way for the two to drift, e.g. `POSTGRES_PASSWORD: ${DOCKTOR_DB_PASSWORD:?Set DOCKTOR_DB_PASSWORD in .env.local}`), or fail loudly if left at the default.

### WR-05: `runRestoreProcess()` silently continues with an empty env object when the backup repository is unconfigured

**File:** `server/src/application/backup-service.ts:362-366`
**Issue:**
```ts
const repoConfig = await this.getBackupRepoConfig()
const env: Record<string, string> = repoConfig ? this.buildEnv(repoConfig, stack.hostPath ?? undefined) : {}
```
`initiateRestore()` fails fast with a clear `BadRequestError("No backup repository is configured...")` when `getBackupRepoConfig()` returns null. `runRestoreProcess()` — invoked immediately afterward — re-fetches the same config and, if it now returns null (e.g. an admin clears the backup settings in the narrow window between the two calls), does not fail with the same clear message; it proceeds to call `resticExecutor.run(["restore", ...], {}, ...)` with no `RESTIC_REPOSITORY`/`RESTIC_PASSWORD`, letting restic itself produce whatever raw error message it produces for a missing repository, which then gets wrapped as a generic backup-record failure instead of the intended, actionable message.
**Fix:** If `repoConfig` is null here, fail immediately with the same `BadRequestError`-equivalent message used in `initiateRestore()` instead of falling back to `{}`.

} catch (err: unknown) {

### IN-02: `findAllStacks()` builds file paths via string concatenation instead of `path.join`

**File:** `server/src/repositories/stack-repository.ts:308-324`
**Issue:**
```ts
composeFilePath: `${s.hostPath}/docker-compose.yml`,
...
envFilePath: `${s.hostPath}/.env`,
```
Inconsistent with `getStackPath()`/`getComposePath()`/`getEnvPath()` in `lib/stacks-dir.ts`, which use `path.join`/`path.resolve` throughout. If `hostPath` ever has a trailing slash, this produces a double-slash path; low risk in the current single-platform (Linux container) deployment, but worth normalizing for consistency.
**Fix:** Use `path.join(s.hostPath, "docker-compose.yml")` / `path.join(s.hostPath, ".env")`.
