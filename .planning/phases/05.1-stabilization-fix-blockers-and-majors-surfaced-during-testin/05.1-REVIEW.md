# Phase 05.1: Code Review Report — Windows path-separator gap closure (G-05.1-4)

**Reviewed:** 2026-09-03
**Depth:** standard
**Files Reviewed:** 6
**Status:** issues_found

## Summary

The core fix — normalizing fast-glob's unconditionally-unixified output with `path.normalize()` at the point it enters `BrownfieldScanner.scan()`, and adding a separator-tolerant `directoryDisplayName()` helper on the client — is correctly implemented and does what its commit message and comments claim: on a real Windows host, `path` (the real, platform-selected `node:path`) will convert fast-glob's forward-slash output to native backslashes before `path.dirname()` is called, and the new win32-mocked test suite pins that behavior credibly (the `vi.mock("node:path", …)` swap to `actual.win32` is a sound way to reproduce a Windows-only bug on Linux CI). No regression was found in the POSIX path either, since POSIX `path.normalize()` on an already-forward-slash string is idempotent aside from harmless `.`/`..`/double-slash collapsing.

That said, four issues degrade the completeness/reliability of this gap closure and one test doesn't actually exercise the scenario it documents. No blocker-level defect was found in the normalize-at-the-boundary fix itself.

## Warnings

### WR-01: Windows system directories are not excluded by `SYSTEM_DIRS`, unlike their POSIX equivalents

**File:** `server/src/infrastructure/brownfield-scanner.ts:46,55-63`
**Issue:** `SYSTEM_DIRS` is hardcoded to POSIX literals (`/proc`, `/sys`, `/dev`) and compared with strict equality against `path.normalize(dir)`. On a native Windows host, the platform-selected `path.normalize()` is win32's, which converts `/proc` to `\proc` — so even a user who types the POSIX spelling by habit will never match this list, and there is no equivalent guard for Windows-sensitive roots (e.g. `C:\Windows`, `C:\ProgramData`) at all. Given this phase's explicit goal is correct behavior on a Windows host, leaving the "don't scan sensitive OS directories" guard completely inert on that platform is a real regression in scope, not just a missed nice-to-have — a scan configured against `C:\` would walk `C:\Windows` unimpeded, whereas the equivalent `/` scan on Linux is protected.
**Fix:** Add platform-appropriate entries (e.g. `String.raw`\`C:\Windows\``, `` `C:\ProgramData` ``, or derive from `process.env.WINDIR`/`process.env.SystemRoot`) and compare using a normalization that matches on the current platform, or generalize the check to a cross-platform "is this a well-known OS root" predicate instead of a literal POSIX-only list.

### WR-02: `directoryDisplayName()`'s output is used unsanitized to build a filesystem-facing default path, and can yield `..`

**File:** `client/src/routes/setup/components/migration-wizard.tsx:54-61`; root helper at `client/src/lib/path-display.ts:16-28`
**Issue:** `bindMountSelections` seeds `newPath: \`./volumes/${directoryDisplayName(path) || "data"}\`` directly from `directoryDisplayName(originalPath)`, where `originalPath` is one of `DiscoveredStack.absolutePaths` — a value read verbatim out of an operator-authored compose file's bind-mount source, not a filesystem-verified path. `directoryDisplayName()` does not strip `.`/`..` segments: for input like `/data/foo/..`, the "last non-empty segment" is `..`, so the produced default is `./volumes/..`, which resolves outside the intended migrated-stack directory. There is no UI control in `MigrationWizard` to edit `newPath` before it is sent to `executeMigration`, so this default is exactly what gets submitted unless the operator notices it in the step-2 diff and cancels. This predates this delta (the prior code had the identical gap via `path.split("/").pop()`), but it remains live in the code introduced/touched by this fix and the new helper's docstring calls it a helper to "safely derive a folder name," which overstates what it guards against.
**Fix:** Either (a) have `directoryDisplayName()` filter out `.`/`..` pseudo-segments (walk back to the nearest real segment, or return `""` and let the caller's `|| "data"` fallback apply), or (b) sanitize/validate `newPath` server-side in the migration executor before it is used for any filesystem operation, so a compose-authored `..` can never escape the target directory regardless of client behavior.

### WR-03: "differently-spelled paths" dedup test does not actually test differently-spelled paths

**File:** `server/test/unit/infrastructure/brownfield-scanner-windows-paths.test.ts:109-125`
**Issue:** The test claims (in its title and the source comment it mirrors) to prove that normalizing before the `Set`-based dedup "collapses two differently-spelled paths to the same file into exactly one stack." But the mock is set up with `mockResolvedValueOnce([...]).mockResolvedValueOnce([...])` using the *identical* string `"C:/Users/D/Stacks/app/docker-compose.yml"` both times — not two different spellings. Since fast-glob's own `absolute: true` output is, per the surrounding comments, *unconditionally* unixified regardless of which `cwd`/scan root produced it, two overlapping scan roots would already yield identical forward-slash strings pre-normalization — the original (pre-fix) `Array.from(new Set(foundFiles))` already deduplicated this case. This test therefore passes regardless of whether `path.normalize()` is present, and does not add the coverage its name and the code comment at `brownfield-scanner.ts:88-92` ("two overlapping scan roots that surface different spellings of one file collapse to one stack") claim it does.
**Fix:** Either construct a genuinely different pre-normalization spelling for the two mock resolutions (e.g. one with a redundant `.`/double-slash segment that `path.normalize()` collapses, such as `"C:/Users/D/Stacks/./app/docker-compose.yml"` vs `"C:/Users/D/Stacks/app/docker-compose.yml"`), or correct the test/comment claim to describe what is actually being verified (that identical fast-glob output dedupes, and that normalize doesn't break that).

### WR-04: `absolutePaths` classification is POSIX-only, contradicting the premise cited for the client-side fix

**File:** Cross-reference: `client/src/lib/path-display.ts:1-7` (docstring) and `client/src/routes/setup/components/migration-wizard.tsx:54-61` vs. `server/src/infrastructure/compose-analyzer.ts:97,100,111` (not in review scope, but load-bearing here)
**Issue:** `path-display.ts`'s file-level comment justifies guarding `DiscoveredStack.absolutePaths` values because "Bind-mount values read out of an operator's compose file … may also be Windows-shaped regardless of where the server runs." However, `compose-analyzer.ts` classifies a bind mount as `type: "absolute"` only when `hostPath.startsWith("/")` (lines 97/100/111) — a Windows-style absolute mount such as `C:\data:/data` or `C:/data:/data` does not start with `/` and is therefore classified `"relative"`, meaning it never reaches `DiscoveredStack.absolutePaths` in the first place. Two implications: (1) the third `directoryDisplayName()` call site in `migration-wizard.tsx` is defending against an input shape that the current pipeline cannot actually produce, so its stated rationale is currently false; and (2) more importantly, a genuinely Windows-authored compose file with an absolute Windows-style bind mount is silently mis-scored — it's missing from `absolutePaths`, so it doesn't trigger the "Absolute path - not recommended" warning in the wizard, and it doesn't push `compatibility` to `yellow`/`red` in `analyzeCompatibility`'s scoring, which understates real migration risk for that stack.
**Fix:** Extend `compose-analyzer.ts`'s absolute-path detection to also recognize Windows-style absolute paths (drive-letter prefix `[A-Za-z]:[\\/]` or UNC `\\`), so `absolutePaths` faithfully reflects Windows-authored compose files too — otherwise scope down `path-display.ts`'s docstring to not claim that guard is currently exercised.

## Info

### IN-01: Unused `AnalysisResult` type import

**File:** `server/src/infrastructure/brownfield-scanner.ts:7`
**Issue:** `type AnalysisResult` is imported from `./compose-analyzer.js` but never referenced anywhere else in the file (the return value of `analyzeCompatibility()` is consumed structurally via `analysis.compatibility`, `analysis.serviceCount`, etc., without ever naming the `AnalysisResult` type). Pre-existing (not touched by this delta's diff), but present in the reviewed file.
**Fix:** Remove the unused import, or use it to explicitly type the local `analysis` variable (`const analysis: AnalysisResult = this.analyzer.analyzeCompatibility(content);`) for documentation value.

### IN-02: No `key` prop tying `MigrationWizard`'s mount identity to the selected stack

**File:** `client/src/components/domain/stack/brownfield-import.tsx:271-279`
**Issue:** `<MigrationWizard stack={migratingStack} .../>` is rendered without a `key`. Because `BrownfieldImport` guards the render with `{migratingStack && ...}`, switching between "no dialog" and "dialog for stack A" forces a fresh mount today, so `MigrationWizard`'s `useState` initializers (which read `directoryDisplayName(stack.directory)`, `stack.namedVolumes`, `stack.absolutePaths` only once, at mount) happen to always run against the correct stack in the current UI (the shadcn `Dialog` overlay blocks clicks on the underlying table while open, so a direct A→B transition without an intervening `null` isn't currently reachable). This is fragile: if the overlay/backdrop behavior ever changes, or another code path calls `setMigratingStack` while the dialog is already open, `MigrationWizard` would keep stale `displayName`/volume-selection state computed from the previous stack.
**Fix:** Add `key={migratingStack.path}` to `<MigrationWizard>` so React always remounts (and thus re-initializes state) when the target stack changes, regardless of overlay/interaction assumptions.
