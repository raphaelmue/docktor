# Phase 05.1: Code Review Report (gap-closure delta: 05.1-09, 05.1-10, 05.1-11)

**Reviewed:** 2026-09-03T00:00:00Z
**Depth:** standard
**Files Reviewed:** 11

## Summary

This pass reviews only the gap-closure delta for three previously-shipped fixes: the
platform-independent Prisma CLI resolver (`prisma-cli.ts`, wired into `schema-sync.ts` and
`server/test/integration/setup.ts`), the `docker-compose.yml` env-file rename from
`.env.local` to `.env` (plus the new `.dockerignore`), and the new `ensureStacksDir()` boot
step (`stacks-dir.ts`, wired into `index.ts`).

The three core code changes are sound: `resolvePrismaCliEntrypoint()` correctly uses Node
module resolution instead of a hardcoded POSIX `.bin` path, both call sites (`schema-sync.ts`,
`server/test/integration/setup.ts`) were updated consistently, and `ensureStacksDir()` is
idempotent, well-tested, and correctly sequenced before `assertStacksDirMatchesHost()`'s
sibling checks in `index.ts`.

However, cross-referencing the `.env` rename against the *other* files that instruct an
operator to create that file surfaced a genuine, currently-shipping regression: the env
template files (`.env.example`, `.env.production`) were never updated and still tell the
reader to create `.env.local` — the exact file Compose's interpolation cannot see, i.e. the
precise bug this phase's plan 05.1-10 was written to eliminate. Separately, the newly-added
`.dockerignore` (also part of 05.1-10, stated purpose: stop uploading operator secrets to the
Docker build context) omits the directory that `docker-compose.yml`'s `db` service actually
persists the production database to, which sits inside the same build context tree.

## Critical Issues

### CR-01: `.env.example` and `.env.production` still instruct operators to create `.env.local`, contradicting the `docker-compose.yml` rename to `.env`

**File:** `.env.example:3`, `.env.production:12`
**Issue:**

`docker-compose.yml`'s `env_file:` entries were renamed from `.env.local` to `.env` in commit
`93adfbb` (plan 05.1-10), specifically because Compose's top-level `${VAR}` interpolation only
ever reads a project-root file named exactly `.env`, never `.env.local` via `env_file:`. The
companion docs commit (`4276f3c`, same plan) explicitly states in its own message: *"docs/deployment.md
and README.md both instructed operators to create .env.local ... Updated every reference to the
new .env filename"* — but its diff only touches `docs/deployment.md` and `README.md`. The two
files an operator is at least as likely to read (they literally `cp` one of them per the
Quickstart) were never updated:

```
$ git show HEAD:.env.example | head -3
# Docktor environment configuration — docker-compose deployment template.
#
# Copy this file to `.env.local` (the file docker-compose.yml's `env_file`
```

```
$ git show HEAD:.env.production | sed -n '11,14p'
# .env.production. Consider either untracking this file (`git rm --cached
# .env.production`) or removing it from .gitignore, whichever better
# matches how you intend to use it; this plan does not change tracking
# unilaterally. Copy this file to `.env.local` (docker-compose.yml's
```

An operator who follows either file's own in-line instruction — rather than the corrected
README/`docs/deployment.md` copy-paste command — will create `.env.local`, and `docker compose
up -d` will then fail (or silently mis-mount the stacks volume, per `docs/deployment.md`
troubleshooting row 9, which documents this exact symptom as something the rename was meant to
prevent). This is the precise regression plan 05.1-10 exists to close, reintroduced through an
un-updated file the fix's own commit message claims to have handled.

**Fix:**
```diff
--- a/.env.example
+++ b/.env.example
@@ -1,7 +1,7 @@
 # Docktor environment configuration — docker-compose deployment template.
 #
-# Copy this file to `.env.local` (the file docker-compose.yml's `env_file`
+# Copy this file to `.env` (the file docker-compose.yml's `env_file`
 # entry loads) and change every value marked CHANGE_ME before running
 # `docker compose up`. See docs/deployment.md for the full quickstart,
```
Apply the equivalent one-line correction in `.env.production`'s header comment as well.

## Warnings

### WR-01: `.dockerignore` does not exclude `dev-data/`, the directory `docker-compose.yml` actually persists the production database to

**File:** `.dockerignore` (new file, all lines); `docker-compose.yml:82`
**Issue:**

`.dockerignore`'s own header states its purpose: *"Keeps the operator's filled-in secrets
... out of the Docker build context — `docker-compose.yml`'s `docktor` service builds with
`context: .`, so every `docker compose up -d` otherwise uploads the whole project directory
... to the Docker daemon."* It excludes `.env`, `.env.local`, `.env.production`, `.git`, and
`.planning`, but not `dev-data/`.

`docker-compose.yml`'s `db` service (the bundled production Postgres for this exact
self-host deployment, not a dev-only file) bind-mounts its data directory here:

```yaml
  db:
    ...
    volumes:
      - ./dev-data/docktor/db:/var/lib/postgresql
```

That path is directly under the repo root — the same tree used as the `docktor` service's
build context (`build: context: .`). `dev-data/` is `.gitignore`d but not `.dockerignore`d, so
after the first successful boot it holds live production database files (session tokens,
password hashes, encrypted SMTP/SFTP/S3/restic credentials via `ENCRYPTION_KEY`). Any
subsequent `docker compose up -d --build` / image rebuild (e.g. after `git pull` to apply an
update, per `docs/deployment.md`'s own upgrade guidance) will tar and transmit that entire
directory to the Docker daemon as part of the build context — exactly the kind of exposure this
`.dockerignore` was added to close, just for a different, more sensitive payload than the `.env`
files it does cover.

**Fix:**
```diff
--- a/.dockerignore
+++ b/.dockerignore
@@ -10,6 +10,10 @@
 /.env.local
 /.env.production
 
+# The self-host db service's bind-mounted Postgres data directory
+# (docker-compose.yml) — contains live production data after first boot.
+/dev-data
+
 # Pure build-context weight; not read by the Dockerfile's COPY lines.
 /.git
 /.planning
```

### WR-02: `getStacksDir()` treats an empty-string `DOCKTOR_STACKS_DIR` as "set", silently resolving to `process.cwd()` — inconsistent with the sibling check and reachable from the new `ensureStacksDir()`

**File:** `server/src/lib/stacks-dir.ts:5`
**Issue:**

```ts
export function getStacksDir(): string {
    return path.resolve(process.env.DOCKTOR_STACKS_DIR ?? "./stacks");
}
```

`??` only falls back on `null`/`undefined`, not on an empty string. If `DOCKTOR_STACKS_DIR` is
present but empty (e.g. a blank `DOCKTOR_STACKS_DIR=` line in `.env`, or a templating tool that
substitutes an unset variable with `""` rather than omitting the key), `path.resolve("")`
returns `process.cwd()` — silently, with no warning. This is now directly reachable from the new
boot-time `ensureStacksDir()` (`server/src/lib/stacks-dir.ts:29`, wired into
`server/src/index.ts:13`), which would happily `mkdir -p` and start using whatever the
container's current working directory happens to be as the "managed stacks directory," with no
error surfaced.

This is also inconsistent with the sibling function in the same file:
`assertStacksDirMatchesHost()` (`server/src/lib/stacks-dir.ts:86`) treats an empty
`DOCKTOR_STACKS_HOST_DIR` as unset via `if (!hostDir)`, correctly catching the empty-string case
and taking the "warn and return" branch — so the two functions in the same module handle the
identical env-var-set-to-empty-string edge case differently, and only one of the two fails
silently.

**Fix:**
```diff
--- a/server/src/lib/stacks-dir.ts
+++ b/server/src/lib/stacks-dir.ts
@@ -2,7 +2,8 @@ import {mkdir} from "node:fs/promises";
 import path from "node:path";
 
 export function getStacksDir(): string {
-    return path.resolve(process.env.DOCKTOR_STACKS_DIR ?? "./stacks");
+    const configured = process.env.DOCKTOR_STACKS_DIR;
+    return path.resolve(configured && configured.length > 0 ? configured : "./stacks");
 }
```
