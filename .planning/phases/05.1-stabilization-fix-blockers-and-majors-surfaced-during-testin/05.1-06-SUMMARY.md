# Phase 05.1 Plan 06: config_error UI visibility and external .env watching Summary

**Stack.configError persisted with a full set/clear lifecycle and rendered as a red badge on both stack views; FileWatcher now also watches and reconciles a stack's `.env` file via its own `lastEnvHash`, fully isolated from compose-change detection.**

## Performance

- **Duration:** ~55 min
- **Started:** 2026-09-02T09:15:00Z (approx.)
- **Completed:** 2026-09-02T10:10:00Z (approx.)
- **Tasks:** 3
- **Files modified:** 11 (7 source, 4 test)

## Accomplishments

- `Stack.configError String?` persists the latest unresolved compose parse error, set in `FileWatcher.handleFileChange()`'s existing catch branch and cleared the moment the file parses again or any deploy/restart/update/backup action runs (via the single `clearConfigChanged()` choke point)
- `Stack.lastEnvHash String?` gives `.env` files their own change-detection hash, completely separate from `lastKnownHash` — chokidar now watches `.env` (exact basename match, not a suffix check), a new `FileWatcher.handleEnvChange()` handles it with no parse step and no writes to compose-owned fields, and `reconcile()`'s 60s fallback covers env drift too
- The already-declared `config_error` SSE event type finally has consumers: `use-stacks.ts` refetches on it, `use-stack.ts` shows a destructive toast with the parser's message and does a background refetch
- Both stack views render `configError`: a destructive Alert with the full parser message on the detail page (can coexist with the yellow config-changed Alert), and a short red "config error" pill in the stack list next to the yellow "config changed" pill
