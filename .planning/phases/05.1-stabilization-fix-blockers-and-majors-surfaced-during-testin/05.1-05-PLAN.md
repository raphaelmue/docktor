<objective>
Give the container a guarded schema-synchronisation step so a fresh `docker compose up` stops failing at runtime with `The table 'public.Backup' does not exist in the current database` (todo item B2).

Purpose: nothing in the image or the compose startup applies the Prisma schema before the server begins serving requests, so the documented self-host quickstart is broken on first run. This is the deployment blocker that makes the product's core "copy-paste this compose file" promise false.
Output: a `syncDatabaseSchema()` startup step with real guards — opt-out, reachability, concurrency lock, and a hard refusal to accept data loss — wired in ahead of `app.listen()`.

**Explicit scope limit — do not adopt `prisma migrate` in this phase.** The user decided on 2026-09-01 to keep schemaless `prisma db push` until the MVP milestone completes, because the schema still changes shape frequently. Do not create `server/prisma/migrations/`, do not run `prisma migrate dev` or `prisma migrate deploy`, and do not change `server/prisma/prisma.config.ts`'s schema strategy. The deferred follow-up is already captured in `.planning/todos/pending/2026-09-01-adopt-prisma-migrate-post-mvp.md` — read it so you do not duplicate or pre-empt it.

Dependency note: plan 05.1-01 investigated whether `prisma db push` works at all against a reachable database in this toolchain. **Read its SUMMARY before starting.** If it found and fixed a defect on that invocation path, this plan inherits the fix; if it concluded the failure was environmental, this plan must still prove `db push` works inside the built container, which Task 3 does.
</objective>

    - with `DOCKTOR_DB_AUTO_PUSH` set to `false`, the function returns a `skipped` result and spawns no child process
    - with the database unreachable for the whole retry budget, the function returns an `unreachable` result, logs an error naming the host and port, and does not throw
    - with the database reachable and the schema absent, the function spawns the Prisma CLI and returns an `applied` result
    - with the schema already current, it returns an `already-current` result derived from the CLI's own already-in-sync output
    - when the advisory lock cannot be acquired, it returns a `lock-not-acquired` result and spawns no child process
    - when the CLI exits non-zero, it returns a `failed` result carrying the child's stderr and does not throw
    - the argument vector passed to the CLI contains no data-loss acceptance flag and no reset flag
    - the advisory lock is released on every path, including when the CLI throws
  </behavior>
  <action>
    Create `server/src/lib/schema-sync.ts` exporting an async function `syncDatabaseSchema()` returning a discriminated result — model it as `{outcome: "skipped" | "unreachable" | "lock-not-acquired" | "already-current" | "applied" | "failed", detail?: string}` so callers and tests can assert on the outcome rather than parse a log line.

    Make it testable by injecting its two effectful collaborators as optional parameters with production defaults: the child-process runner (default: spawn the Prisma CLI) and the lock acquirer (default: a `pg` client taking a Postgres advisory lock). Follow the repo's existing dependency-injection convention — constructor/parameter injection with a production default, as `FileWatcher` and `StatePoller` do — so the unit tests need neither a database nor a subprocess.

    Guards, all four required:

    1. **Opt-out.** Read `DOCKTOR_DB_AUTO_PUSH`. The step runs unless the value is exactly `false`. Absent means enabled, so an existing deployment that adds nothing still gets the fix.
    2. **Reachability.** Before spawning anything, open a plain `pg` connection with a short per-attempt timeout and retry with backoff up to a bounded total budget (a handful of attempts over roughly thirty seconds is right — the compose file already gates on `db: condition: service_healthy`, so this only covers the residual race). On exhaustion, log an error naming the host and port from `DATABASE_URL` and return `unreachable` without throwing. Do not let an unreachable database stop the HTTP server from booting — Phase 02 already established that a single failing startup step must not take the whole process down.
    3. **Concurrency.** Take a Postgres session-level advisory lock with a fixed application-chosen integer key before spawning the CLI, using the non-blocking try-variant, and release it in a `finally`. If the lock is already held, return `lock-not-acquired` and spawn nothing — this is what makes the step safe against two instances starting against one database, which is the specific hazard that caused this fix to be deferred in the first place.
    4. **No data loss.** Build the CLI arguments as an argv array — never a shell string — containing only the push subcommand and the `--config` path pointing at `server/prisma/prisma.config.ts`. It must never include a flag that accepts data loss, and never a reset flag. If the CLI refuses the push because it would drop data, that non-zero exit is the correct outcome: return `failed` with the captured stderr and a log line telling the operator to resolve the schema conflict manually. Silently destroying a self-hoster's data is strictly worse than not starting cleanly.

    Resolve the Prisma CLI binary and the config path from the module's own location rather than assuming a working directory, mirroring how `server/test/integration/setup.ts` resolves them, because the container's `CMD` runs from `/app` while the compiled module lives under `/app/dist/server`.

    Write the unit tests in `server/test/unit/lib/schema-sync.test.ts` first — one per case in `<behavior>` — using injected fakes for the runner and the lock. Confirm they fail, then implement.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| container startup -> production database | an unauthenticated, unprompted process mutates the live schema before any request is served |
| Node process -> spawned Prisma CLI | an argv and an environment carrying `DATABASE_URL` cross into a child process |
| instance -> instance | two containers may start against one database concurrently |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05.1-20 | Denial of Service / destructive change | the startup `db push` against a populated database | high | mitigate | Task 1 forbids any data-loss-acceptance or reset flag in the argv, asserted by a unit test that inspects the argv array. A push that would drop data must fail loudly and leave the data intact — this is the single most important guard in the plan, and the reason the naive version of this fix was rejected when the todo was filed |
| T-05.1-21 | Tampering | two instances applying the schema simultaneously | high | mitigate | Task 1's non-blocking Postgres advisory lock; the losing instance skips entirely. This is the second reason the fix was originally deferred |
| T-05.1-22 | Denial of Service | schema step blocking the process on an unreachable database | medium | mitigate | Task 1's bounded reachability budget returns `unreachable` and never throws; Task 2 requires startup to continue so the operator can still reach the container and read the logs. Mirrors the Phase 02 fix where an unguarded `startJobs()` took down the whole process on a cold start |
| T-05.1-23 | Information Disclosure | logging the CLI's stderr and the reachability failure | medium | mitigate | Log only the host and port parsed out of `DATABASE_URL`, never the full URL — it carries the database password. Pass `DATABASE_URL` to the child through its environment only; never interpolate it into a command string or a log line |
| T-05.1-24 | Tampering (command injection) | spawning the Prisma CLI | medium | mitigate | Task 1 requires an argv array, not a shell string. The only interpolated values are paths resolved from the module's own location, but the argv form removes the class of bug entirely |
| T-05.1-25 | Elevation of Privilege | an operator disabling the guard | low | accept | `DOCKTOR_DB_AUTO_PUSH=false` only turns the step off; there is no value that turns on destructive behaviour, because no such code path exists |

No package-manager install occurs in this plan, so no package-legitimacy gate applies.
</threat_model>
