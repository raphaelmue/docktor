# Phase 05.1 Plan 04: Backup guard against missing repository + SSE broadcasts for backup/restore Summary

**BackupService.initiateBackup()/initiateRestore() now reject with a 400 before mutating any state when no backup repository is configured, and every backup/restore status transition now broadcasts stack_status over SSE via the same non-throwing-guard pattern plan 05.1-02 established for StackService.**

## Accomplishments

- `initiateBackup()` and `initiateRestore()` now call `getBackupRepoConfig()` after their existing stack-existence guard and throw `BadRequestError` when it resolves `null`, before creating any `Backup` row or writing any stack status — closing todo M4 (a backup/restore request with no configured repository can no longer permanently wedge a stack in `BACKING_UP`/`RESTORING`)
- Verified (Task 2) that the fire-and-forget defence-in-depth path in `routes/backups.ts` already resolves an unconfigured backup out of `BACKING_UP` via `abortBackup()` — this had already landed during Phase 04, contrary to the todo's original "TBD" framing; three regression tests locking in `abortBackup()`'s idempotency and terminal-frame guarantees were already present and passing, so no new tests were needed for this task
- `BackupService` now takes a `broadcaster: Pick<StateBroadcaster, "publish">` constructor param (wired to the existing `stateEventBroadcaster` singleton), and every status-mutating `stackRepo.update()` call site — `initiateBackup`, `initiateRestore`, `runBackup` (both outcomes), `runRestoreProcess` (both outcomes), `abortBackup`, and `recoverInProgressBackups` — now routes through a single private `writeStackStatus()` wrapper that publishes `stack_status` after the write resolves, with the publish itself guarded so a throwing SSE subscriber can never propagate
- Closes the backup/restore half of todo M3 (the `stack-service.ts` half landed in plan 05.1-02)

This is a pre-existing gap outside Task 1's stated acceptance criteria (RESTORE's allowed-from list doesn't include any transitional status, and `runRestoreProcess()` unconditionally stops the stack regardless of its starting status before restoring, so it isn't a stranding risk of the same class the missing-repo guard closes) — left unfixed per the scope-boundary rule, logged here for visibility rather than silently expanding scope.
- `recoverInProgressBackups()`'s status write was also routed through `writeStackStatus()` even though it wasn't named in Task 3's `read_first` file-list enumeration — required by the acceptance criteria's grep check (no remaining direct `stackRepo.update({status})` call outside the helper) and consistent with the plan's broader goal (every status transition should broadcast).
- The `BadRequestError` message is copied verbatim from `routes/backups.ts`'s existing fire-and-forget branch so the user sees one consistent error string regardless of which guard caught the missing configuration.
