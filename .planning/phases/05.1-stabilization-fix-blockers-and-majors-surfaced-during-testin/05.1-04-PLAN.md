<objective>
Stop a backup request from wedging a stack forever when no backup repository is configured (todo item M4), and extend the SSE status broadcasting added in plan 05.1-02 to the backup and restore flows (the `backup-service.ts` half of todo item M3).

Purpose: `BackupService.initiateBackup()` unconditionally creates an `IN_PROGRESS` Backup row and moves the stack to `BACKING_UP` without ever checking that a repository exists. `BACKING_UP` appears in no action's allowed-from list in `stack-status-machine.ts`, and `StatePoller` unconditionally skips transitional statuses — so once a stack lands there without a running backup, there is no in-app recovery path at all, only a manual database edit.
Output: fail-fast validation before any state is mutated, verified defence in depth on the fire-and-forget path, and live status broadcasts for backup and restore.

Scope boundary: `stack-service.ts` and its transitions belong to plan 05.1-02, which lands first; this plan reuses the broadcaster convention that plan establishes.
</objective>

Contracts to build on, not redefine:

- `BackupService` constructor is `(resticExecutor, backupRepo, stackRepo, settings, notificationService, filesystem, docker)`; the singleton is built in `server/src/application/index.ts`. `stackRepo` is the `BackupStackRepo` adapter declared in that same file, whose `update(id, data)` is what performs every stack status write in this service — it is not `StackRepository.transitionStatus`.
- `BackupService.getBackupRepoConfig()` already returns `Promise<BackupRepoConfig | null>` and returns `null` precisely when `backup.repoType` is unset. That is the existing "is a repository configured" predicate — use it, do not invent a second one.
- `BackupService.abortBackup(backupId, stackId, errorMessage)` already exists, is idempotent (no-ops unless the row is still `IN_PROGRESS`), marks the row `FAILED`, transitions the stack to `ERROR`, notifies, and always emits the terminal `done` frame in a `finally`.
- `server/src/lib/errors.ts` exports `BadRequestError` (400); the global Fastify error handler in `app.ts` converts it. Do not add an HTTP status anywhere else.
- `server/src/lib/state-broadcaster.ts` already declares `StackStatusEvent {type, stackId, stackStatus}` and exports `stateEventBroadcaster`. Plan 05.1-02 established the convention of injecting `Pick<StateBroadcaster, "publish">` through the constructor and guarding every `publish` so a throwing subscriber cannot strand a transitional status — read its SUMMARY and follow it exactly.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated client -> `POST /api/stacks/:id/backup` and `/restore` | an authenticated request drives a state machine and spawns a restic process |
| server -> every subscribed SSE client | `stateEventBroadcaster.publish` fans out to every open `/api/events` connection |
| `BackupService` -> restic subprocess | repository credentials are passed through the child environment |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05.1-15 | Denial of Service | `initiateBackup` / `initiateRestore` transitioning into `BACKING_UP`/`RESTORING` with no repository | high | mitigate | Task 1: reject before any state write. Today any authenticated user can permanently disable a stack — `BACKING_UP` is in no allowed-from list and `StatePoller` skips transitional statuses unconditionally, so the only recovery is a manual database edit |
| T-05.1-16 | Denial of Service | a throwing SSE subscriber inside `abortBackup`'s `try` block | high | mitigate | Task 3 wraps every publish. An exception escaping there would skip the `finally` that emits the terminal `done` frame and disposes the broadcaster, leaving every subscribed client on a stream that never ends |
| T-05.1-17 | Information Disclosure | the `BadRequestError` message returned for an unconfigured repository | low | mitigate | Task 1 fixes the message to name only the missing configuration and its Settings location. It must not echo any part of `getBackupRepoConfig()`'s return value, which carries decrypted SFTP keys, S3 secrets and the restic password |
| T-05.1-18 | Information Disclosure | `stack_status` events published from backup flows | low | mitigate | Publish only the fields `StackStatusEvent` declares. Never widen a status event to carry a restic error string — `runBackup`'s error text can contain repository URLs and paths, and every authenticated session receives every event |
| T-05.1-19 | Repudiation | backup rejections leaving no trace | low | accept | A rejected request creates no Backup row by design (that is the fix); the rejection is visible to the caller as a 400 and in the server log. A dedicated audit row for refused backups is not warranted at ASVS L1 for a single-admin deployment |

No package-manager install occurs in this plan, so no package-legitimacy gate applies.
</threat_model>
