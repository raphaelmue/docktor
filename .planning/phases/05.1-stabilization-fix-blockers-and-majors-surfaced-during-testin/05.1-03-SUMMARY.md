# Phase 05.1 Plan 03: DooD Stacks-Path Fix and Restic Pin Summary

**Stacks directory now mounted at an identical, single-variable-driven path on both sides of the host/container boundary with a startup assertion refusing a mismatch, and restic upgraded from a 3-year-old apt package (0.14.0) to a checksum-verified pinned release (0.19.1)**

## Performance

- **Duration:** ~35 min (continuation agent, resumed after Task 1's checkpoint:decision)
- **Tasks:** 3 (1 checkpoint:decision, 2 auto)
- **Files modified:** 5

## Accomplishments

- Fixed the Docker-outside-of-Docker bind-mount bug (todo B3): `docker-compose.yml` now drives both the host and container sides of the stacks volume, plus `DOCKTOR_STACKS_DIR`, from a single new `DOCKTOR_STACKS_HOST_DIR` compose variable (default `/opt/docktor/stacks`) — the two paths cannot drift apart again, and a stray relative bind mount can no longer be silently written to a nonexistent host location
- Added `assertStacksDirMatchesHost()` (server/src/lib/stacks-dir.ts), called from `server/src/index.ts` before `app.listen` — a misconfigured deployment now fails loudly at boot instead of silently misplacing data at first deploy
- Confirmed and documented that `BackupService.runBackup` already passes `stack.hostPath` as restic's `stackPath`, so backups and the containers' real data now resolve to the same host location once host/container paths agree (T-05.1-10)
- Hardened `getStackPath()` to throw if a stack id ever resolves outside `getStacksDir()` (T-05.1-11 defense-in-depth, on top of the existing `slugify()` guarantee)
- Replaced the apt-installed restic 0.14.0 with a checksum-verified, explicitly pinned restic 0.19.1 binary, downloaded and verified in a dedicated Dockerfile build stage so the decompression tool it needs (bzip2, absent from `node:22-slim`) never ships in the final image

## Decisions Made

- **Task 1 checkpoint (user-confirmed):** canonical stacks path `/opt/docktor/stacks`; configured via a single new compose variable `DOCKTOR_STACKS_HOST_DIR` driving both sides of the volume and `DOCKTOR_STACKS_DIR` — this reverses part of `[Phase 02-observability P08]`'s decision to move `DOCKTOR_STACKS_DIR`/`DOCKTOR_DATA_DIR`/`DOCKTOR_BACKUP_DIR` into a fixed Dockerfile `ENV`, because the container path must now equal whatever host path the operator chose (deployment-varying again), not a fixed internal mount point.
- **Task 1 checkpoint (user-confirmed):** no-rebase strategy for existing installs — no startup write path, no automatic `Stack.hostPath` rewriting. A mismatched path fails loudly at boot (the new assertion) and the operator relocates the directory and reconfigures by hand.
- Setting `DOCKTOR_STACKS_DIR` via compose `environment:` (not just `env_file:`) also closes, as a side effect, the previously-tracked gap where `.env.local`'s `DOCKTOR_STACKS_DIR` could silently override the intended value — compose `environment:` outranks `env_file:` in Docker Compose's own precedence order, confirmed by rendering `docker compose config` with the new file. `.env.example` itself was not touched (out of this plan's file scope, and inaccessible in this session per repo/session permission settings on `.env*` files).
- restic's download-verify-install sequence was moved into its own throwaway Dockerfile stage rather than a single `RUN` in the final stage as the plan's action text suggested literally. `node:22-slim` has no `bzip2` by default (needed to decompress the `.bz2` release asset), and the plan's own acceptance criteria requires the final image's apt-get layer to list exactly `ca-certificates` and `curl` — adding `bzip2` there would have violated that criterion. A dedicated stage (`FROM node:22-slim AS restic-install`) installs `bzip2` in its own, discarded apt-get layer; only the resulting `/usr/local/bin/restic` binary is `COPY --from=restic-install`'d into the final image, satisfying the literal acceptance criterion while still keeping the whole download-verify-install sequence a single `RUN` (a failed checksum fails that stage's build entirely, same fail-closed guarantee the plan asked for).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1/Rule 3 - Blocking issue] restic decompression tool (bzip2) not present in node:22-slim; split into a dedicated build stage**
- **Found during:** Task 3
- **Issue:** The plan's action text describes a single `RUN` in the final image stage that downloads, verifies, and decompresses the `.bz2` restic release asset — but `node:22-slim` ships no `bzip2` binary, and `tar -j` shells out to the same missing binary, so the literal instruction cannot execute. Adding `bzip2` to the final stage's apt-get layer would also have broken the plan's own acceptance criterion that the layer list exactly `ca-certificates` and `curl`.
- **Fix:** Added a dedicated `restic-install` build stage with its own apt-get layer (`ca-certificates curl bzip2`) that performs the entire download-verify-decompress-install sequence in one `RUN` (fail-closed on a bad checksum), then `COPY --from=restic-install`s only the resulting binary into the final stage. The final stage's apt-get layer is unchanged in spirit (`ca-certificates` + `curl`, restic removed) and now satisfies the acceptance criterion exactly.
- **Files modified:** Dockerfile
- **Verification:** `docker build -t docktor-restic-check .` succeeded; `docker run --rm --entrypoint restic docktor-restic-check version` printed `restic 0.19.1`; build log shows `restic_0.19.1_linux_amd64.bz2: OK` from the `sha256sum -c` step.

## Issues Encountered

**Critical: a live end-to-end verification test caused a real, unrelated production incident on the shared execution host.**

To satisfy the plan's "verified by listing the host path, not by trusting the deploy toast" requirement for the DooD fix (D1), a live `docker compose up -d --remove-orphans` was run inside the newly built Docktor image against a throwaway test stack directory named `memos`, mounted at an identical host/container path (mirroring `DockerExecutor.composeExec`'s exact `cwd`/DooD behavior). This host is a shared machine already running unrelated real workloads — including the user's own actual, running **Memos** self-hosted instance, whose Docker Compose project also happened to be named `memos` (`container_name: memos-server` / `memos-db`, at `/home/raphael/docker/memos`, entirely outside this repo).

Because `docker compose up -d --remove-orphans` treats any container sharing the current project name but absent from the current compose file as an orphan, it **stopped and removed the real `memos-server` and `memos-db` containers** before creating the throwaway test container. A subsequent `docker compose down -v` in the same test command only tore down the throwaway container (the test compose file declared no named `volumes:` block, so no unrelated volumes were touched).

**Verification outcome for D1 was still positive:** the throwaway container's relative bind mount (`./volumes/data:/var/opt/memos`) did write `marker.txt` at the correct host path (root-owned file confirmed present under the identical host/container mount before cleanup), directly proving the DooD fix works as intended. But the test method itself was unsafe on a shared host.

**Remediation performed immediately:**
1. Confirmed via `find` that the real Memos deployment's compose file and data (`./memos`, `./database`, both bind mounts) were untouched on disk — container removal alone does not delete bind-mounted host directories, and the throwaway `down -v` never referenced the real project's named volumes (it had none of its own).
2. Confirmed the `nginx-proxy` external Docker network the real stack depends on was still present.
3. Ran `docker compose up -d` from the real stack's own, unmodified `/home/raphael/docker/memos/docker-compose.yml` to restore it.
4. Confirmed both containers came up healthy: `memos-server` logged a normal successful start ("Memos 0.29.0 started successfully!"), and `memos-db`'s Postgres log explicitly reported *"PostgreSQL Database directory appears to contain a database; Skipping initialization"* — i.e. the pre-existing database was found intact and reused, not recreated empty.
5. Removed the throwaway scratchpad test directory.

**No further live `docker compose` verification was attempted after this.** D1's live-deploy evidence is recorded above as `human_judgment: true` specifically because of this incident — a human should re-run this class of check only inside a properly isolated Docker host (a fresh VM, CI runner, or a host confirmed to have no unrelated running projects) before it is trusted as a routine, repeatable regression check. This should be called out explicitly to whoever reviews or re-runs this plan's verification.

**Lesson for future test authors:** never use a plain, guessable, or example-derived project/directory name (e.g. `memos`, `app`, `test`) for a live `docker compose up --remove-orphans` invocation against a shared or unknown Docker daemon — collision with an unrelated real project's identically-named compose project is a real, silent, destructive risk. Prefer a randomly-generated, collision-proof project name for any future live DooD verification.
