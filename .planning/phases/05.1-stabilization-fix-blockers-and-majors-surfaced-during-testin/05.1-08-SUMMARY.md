# Phase 05.1 Plan 08: Deployment Docs, Env Templates, and Compose Finalization Summary

**Rewrote `.env.example`/`.env.production` from a fresh `process.env` grep (14 variables, zero dead config), finalised `docker-compose.yml` as the documented self-host deployment, wrote `docs/deployment.md` and a new `README.md`, and — discovered only by literally running the quickstart being documented — fixed two real bugs (`schema-sync`'s `--skip-generate` flag and `DiskChecker`'s server-crashing unguarded query) that were silently breaking every fresh deploy.**

## Accomplishments

- `.env.example`/`.env.production` now document exactly the 14 `process.env` variables the server actually reads (re-derived from a fresh grep, not copied from the old template), each with a comment on purpose, required/optional status, and default. Dropped the three confirmed-dead variables (`DOCKTOR_BASE_URL`, `DOCKTOR_DATA_DIR`, `DOCKTOR_BACKUP_DIR`). Closed the standing todo where `DOCKTOR_STACKS_DIR`'s template value silently overrode the correct docker-compose default via `env_file` — the live line is now the canonical `/opt/docktor/stacks`, with the `yarn dev` host-run value only as a commented alternative. Also fixed `DATABASE_URL`'s host (`localhost` → `db`, the actual compose service name) and defaulted `DOCKER_DATA_PATH` to `/host/var/lib/docker` so disk-space monitoring reflects real host disk instead of the container's own throwaway filesystem.
- `docker-compose.yml` is now the documented self-host deployment (its "not for production" disclaimer removed), with the decorative `/data` and `/backups` mounts dropped, Postgres no longer publishing 5432 to the host (T-05.1-42), and an inline comment on every service/volume including the security implications of the Docker-socket and `/host:ro` mounts. `docker-compose.dev.yml` got a header comment stating it's dev-database-only and its Postgres bumped from 17 to 18 to match.
- `docs/deployment.md` covers prerequisites, a quickstart, a complete env-var reference table, a dedicated stacks-directory-path section, a database-schema section, a backups section, and an 8-row troubleshooting table mapping every finding from the 2026-08-27 todo to its cause and fix. `README.md` (new — none existed) gives a short project overview and points at the deployment doc.
- **Found and fixed two real, previously-undetected production bugs** while literally executing the quickstart against a real build of this plan's own `docker-compose.yml`: (1) `schema-sync.ts`'s `prisma db push` argv included `--skip-generate`, a flag this project's Prisma CLI (7.4.0) rejects outright — the 05.1-05 startup schema-sync step had been silently failing on every single invocation since it was built; (2) `DiskChecker.check()`'s unguarded settings query, invoked fire-and-forget, crashed the entire server process via an unhandled promise rejection on a fresh database, restart-looping under `restart: unless-stopped`. Both fixed with unit test coverage; both blocked this plan's own acceptance criteria and would have made the newly-written quickstart false as written.
- Live-verified the fixed quickstart end-to-end via container-to-container HTTP (this sandbox blocks host-shell TCP payload delivery to Docker-published ports, confirmed again here — see 05.1-01/05.1-05): fresh empty database → `[schema-sync] applied` → `GET /api/setup/status` → `200 {"setupComplete":false}` → `GET /` → `200 text/html` (real SPA, not a backend-only install) → `POST /api/setup/step1` successfully created an admin account. This closes 05.1-05's previously-blocked D3 cold-start proof.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1/Rule 3 - Bug + blocking issue] `schema-sync.ts`'s `--skip-generate` argv flag is invalid for this project's Prisma CLI, so the 05.1-05 startup schema-sync step never actually worked**
- **Found during:** Task 3, first live `docker compose up` against the finalised compose file
- **Issue:** `prisma db push --skip-generate` failed with `unknown or unexpected option` on every invocation (confirmed via `prisma db push --help` inside the built image, which lists only `-h/--help`, `--config`, `--schema`, `--url`, `--accept-data-loss`, `--force-reset`). The step logged a "failed" outcome and let the server start anyway (as designed), but the schema was never actually applied — meaning the very blocker this step exists to fix (fresh deploy 500s on missing tables) was still fully present.
- **Fix:** Removed `--skip-generate` from `buildArgv()`. `prisma generate` already runs at Docker build time, so it was never needed at this step anyway.
- **Files modified:** `server/src/lib/schema-sync.ts`, `server/test/unit/lib/schema-sync.test.ts`
- **Verification:** Rebuilt the image; live log showed `[schema-sync] applied: ...`; `GET /api/setup/status` returned `200 {"setupComplete":false}` against the same empty database that previously crashed on `relation "public.Setting" does not exist`. New unit test asserts `--skip-generate` is never in the argv.
- **Committed in:** `b423d76`

**2. [Rule 1/Rule 2 - Bug + missing fault isolation] `DiskChecker.check()`'s unguarded settings query crashed the entire server process**
- **Found during:** Task 3, same live verification session (immediately downstream of bug 1 — the crash happened while the Setting table still didn't exist)
- **Issue:** `check()` is invoked fire-and-forget (`void this.check()`) from both `start()` and its daily cron tick. Its `this.settings.getMany()` call was not wrapped in try/catch (only the later `statfs()` call was). An unhandled rejection here becomes an unhandled promise rejection that crashes the whole Node process — not just the DiskChecker job — taking the HTTP server down with it and restart-looping under `restart: unless-stopped`. This is the same class of bug already fixed for `BackupService.recoverInProgressBackups()` on 2026-08-30 (per STATE.md), but the fix there didn't reach this fire-and-forget call site.
- **Fix:** Wrapped the entire `check()` body in try/catch, matching the fault-isolation pattern every other job already gets from `startJobs()`'s per-job try/catch (which cannot reach a fire-and-forget internal call). Extracted the post-guard logic into a private `checkDiskUsage()` helper for clarity.
- **Files modified:** `server/src/jobs/disk-checker.ts`, `server/test/unit/jobs/disk-checker.test.ts`
- **Verification:** `yarn workspace @docktor/server test test/unit/jobs/disk-checker.test.ts --run` — 8/8 passing including the new fault-isolation test; live redeploy after both fixes produced zero DiskChecker-related crashes across the whole verification session.
- **Committed in:** `b423d76`

## Issues Encountered

**The host this session runs on is a shared machine with ~76 other real, unrelated running containers** (confirmed via `docker ps -a` before any live testing — a real Memos instance, Nextcloud, Immich, Vaultwarden, and dozens more). Per this plan's explicit host-safety instructions and the precedent set by 05.1-03's incident, all live `docker compose` verification in this plan used a distinctive `-p docktor-quickstart-verify-<random>` project name and never `--remove-orphans` against a name not minted for the test. No collision occurred; `docker ps -a`/`docker images` were checked clean before and after, and all test containers, images, and bind-mounted data (`dev-data/docktor/`, `/opt/docktor/stacks`, created as root by the Docker daemon and removed via a throwaway `alpine` container) were fully cleaned up.

**This sandboxed execution session cannot receive a TCP payload from any Docker-published port** — the same confirmed environmental restriction documented in 05.1-01 and 05.1-05 (SYN-ACK completes instantly, `curl` from the host shell then hangs and times out). Re-confirmed here (`curl --max-time 5` → exit 28) before switching to container-to-container HTTP (`docker run --network <compose-network> curlimages/curl ...`) as the verification technique, which worked immediately and cleanly. This is not a code defect in this repository.
