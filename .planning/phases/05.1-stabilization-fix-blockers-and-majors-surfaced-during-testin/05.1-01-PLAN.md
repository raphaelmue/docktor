<evidence_captured_during_planning>
The planner ran both suites before writing this plan. **Important caveat: the planner's shell was sandboxed and outbound TCP from spawned child processes was blocked, while bash's own `/dev/tcp` was not.** Treat everything below as observations to confirm or refute in your own (unsandboxed) environment — not as a settled root cause. Confirm first, then fix.

Server integration (`yarn workspace @docktor/server test:integration`), exit 1:

- `Test Files 3 failed (3)` / `Tests 12 skipped (12)` — all three files died in `beforeAll`, so no test body ever ran.
- Primary error, once per file: `Error: P1001: Can't reach database server at localhost:<port>` thrown from `server/test/integration/setup.ts:35`, i.e. the `execSync(\`${prismaBin} db push --config=${prismaConfigPath}\`)` call.
- Secondary, cascading error, once per file: `TypeError: Cannot read properties of undefined (reading 'statusLog')` at `server/test/integration/setup.ts:71` inside `cleanDatabase()`. This is pure noise: `startContainer()` threw before assigning `prismaClient`, so `beforeEach` then fails on an undefined client and buries the actionable P1001 under a useless TypeError.
- The Postgres testcontainers were genuinely healthy at the moment Prisma reported them unreachable: `docker ps` showed `postgres:17 ... Up (healthy)` with `0.0.0.0:32814->5432/tcp`, `pg_isready -U docktor -d docktor_test` inside the container returned `accepting connections`, and a raw TCP connect from bash to both `127.0.0.1:32814` and `[::1]:32814` succeeded.
- The same P1001 reproduces **outside** the harness, and also against the long-running dev database:
  `DATABASE_URL="postgresql://docktor:docktor@127.0.0.1:5432/docktor" ./node_modules/.bin/prisma db push --config=server/prisma/prisma.config.ts` -> P1001. So whatever it is, it is not specific to testcontainers.
- A pure-JS `pg` client from a spawned `node -e` process also timed out against that same reachable port. **That is the signal that the planner's environment, not the repo, was the blocker** — and it is exactly the discriminator to re-run first.
- Container leak observed: 20 `postgres:17` testcontainers were still running, the oldest 3 days old (i.e. predating the planner's runs — these came from the developer's own earlier runs). `stopContainer()`'s `afterAll` does not run when `beforeAll` throws, so every failed run strands a container.
- Prisma toolchain in use: `prisma 7.4.0` / `@prisma/client 7.4.0`, `server/prisma/schema/base.prisma` declares `datasource db { provider = "postgresql" }` with no `url`, and `server/prisma/prisma.config.ts` supplies `datasource.url` from `process.env.DATABASE_URL`. Probing with a driver-adapter-based config instead produced `Error: The datasource.url property is required in your Prisma config file when using prisma db push`, i.e. the current config shape is the one Prisma itself asks for.

Client e2e (`yarn workspace @docktor/client test:integration`): printed `Running 69 tests using 3 workers` and then produced no further output before being killed at 240s (exit 124). No per-test result was ever emitted, because the configured reporter is `html` only. Structural observation independent of the environment: `client/playwright.config.ts`'s `webServer` starts only `yarn workspace @docktor/client exec vite` on :5173; nothing starts the Fastify API on :3000, which is the origin `client/src/lib/api.ts` and `client/src/hooks/use-container-events.ts` hardcode when `location.port === "5173"`. Specs such as `client/test/integration/auth.spec.ts` stub individual endpoints with `page.route(...)`, so some tests are self-sufficient — but any request not stubbed falls through to an origin nothing is listening on.

    Twenty `postgres:17` testcontainers were found running on the developer's host during planning, the oldest three days old — one stranded per failed integration run. Cause: when `startContainer()` throws, the matching `afterAll(stopContainer)` never gets a chance to stop the container it already started.

    Restructure `startContainer()`/`stopContainer()` in `server/test/integration/setup.ts` so the started container is always stopped: assign the container handle to the module-level `container` binding immediately after `.start()` resolves and before any further work (the `prisma db push` step and the `PrismaClient` construction), and make `stopContainer()` tolerate a partially-initialised state — stop the container even when `app` or `prismaClient` was never assigned, and never let a failure stopping one of the three resources prevent the other two from being released. Additionally register the teardown so it runs even when the `beforeAll` hook rejects; if the chosen mechanism is a Vitest `onTestFinished`/global teardown rather than the existing `afterAll`, say so in the SUMMARY.

    Also decide and record whether testcontainers' Ryuk reaper is enabled in this environment; if it is disabled (`TESTCONTAINERS_RYUK_DISABLED`), note that the explicit teardown above is the only cleanup path and must therefore be airtight.

    Do not clean up the pre-existing stranded containers as part of the code change; list the cleanup command in the SUMMARY so the developer can run it deliberately.
  </action>
