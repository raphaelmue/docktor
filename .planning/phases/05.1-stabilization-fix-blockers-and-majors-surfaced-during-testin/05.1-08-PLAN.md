<objective>
Turn the deployment path into the documented, copy-pasteable quickstart the product's value proposition depends on (todo item M1): a complete `.env.example`, a clean self-host `docker-compose.yml`, and real documentation in the repository.

Purpose: Docktor is a self-hosting management platform, so a broken or undocumented deployment path is a defect in the core product, not a docs chore. Three separate deployment defects during Phase 02 verification were found by trial and error rather than caught by documentation — including an unhelpful BetterAuthError crash at boot from a missing secret with no template entry, and a phantom "no frontend" symptom caused by the wrong NODE_ENV.
Output: an accurate env template, a final compose file, and `docs/deployment.md` plus a `README.md` that points at it.

This plan lands last on purpose. Its compose-file deliverable must already contain plan 05.1-03's same-path stacks mount and rely on plan 05.1-05's startup schema step, so what gets documented is the final correct thing rather than something that then needs re-editing. Read both of those SUMMARYs before starting.

Also subsumed here, because it is the same one-line surface: `.planning/todos/pending/2026-08-30-env-example-stacks-dir-breaks-docker-compose.md`, where the template's `DOCKTOR_STACKS_DIR` value silently overrides the image default through the compose `env_file` entry and sends stack data to an unmounted container path where it is lost on container recreation. Close that todo as part of Task 1.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05.1-39 | Information Disclosure | committed env templates | high | mitigate | Task 1 requires every secret slot to be an obvious placeholder with a replace-me comment. A real BETTER_AUTH_SECRET, ENCRYPTION_KEY or database password committed into a tracked template is a permanent repository-history leak. Also flag for the user that `.gitignore` lists `.env.production` while the file is tracked, so a future edit could commit a real secret without anyone noticing |
| T-05.1-40 | Spoofing | a documented default BETTER_AUTH_SECRET | high | mitigate | The quickstart must require generating a secret, never ship a usable default. A shared known signing secret across deployments would let anyone forge a session for any Docktor instance that followed the doc |
| T-05.1-41 | Information Disclosure | a documented default ENCRYPTION_KEY | high | mitigate | Same treatment. This key encrypts SMTP passwords, SFTP keys, S3 secrets and the restic repository password at rest; a shared documented value makes all of them recoverable by anyone who reads the doc |
| T-05.1-42 | Tampering | the documented compose file exposing Postgres on a host port | medium | mitigate | The current file publishes 5432 to the host. Decide during Task 2 whether the documented self-host deployment needs that, and default to not publishing it — nothing outside the compose network requires it, and the credentials are the well-known template pair |
| T-05.1-43 | Elevation of Privilege | documenting the Docker socket and host-root mounts | medium | mitigate | `/var/run/docker.sock` and `/:/host:ro` grant the container host-root-equivalent reach. The doc must state that plainly in the quickstart, so an operator makes an informed choice rather than pasting it unexamined |
| T-05.1-44 | Repudiation | documentation drifting from the shipped files | medium | mitigate | Task 3's human check requires following the doc literally against the actual repository, which is what catches drift. The written rule is that the doc describes what exists, never an intended state |

No package-manager install occurs in this plan, so no package-legitimacy gate applies.
</threat_model>
