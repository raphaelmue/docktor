# Phase 05.1 Plan 05: Guarded Startup Schema Sync Summary

**`syncDatabaseSchema()` runs a guarded `prisma db push` before `app.listen()` — opt-out env var, bounded reachability retries, a non-blocking Postgres advisory lock, and an argv that can never accept data loss — wired into `server/src/index.ts` and the Docker image, fully unit-tested; the live cold-start proof itself was blocked by this session's confirmed inability to receive TCP payloads from any Docker-published port.**

## Accomplishments

- Built `syncDatabaseSchema()` (`server/src/lib/schema-sync.ts`), a fully unit-tested, injectable startup step that applies `prisma db push` behind four guards: `DOCKTOR_DB_AUTO_PUSH=false` opt-out, a bounded (~30s) reachability retry budget over a raw `pg` connection, a non-blocking Postgres session advisory lock so two instances can never both apply the schema, and an argv array that structurally cannot carry a data-loss-acceptance or reset flag.
- Wired the step into `server/src/index.ts` ahead of `buildApp()`/`app.listen()`, reordering the file per the plan so the DooD stacks-path assertion (05.1-03) still runs first, then schema sync, then app construction, then listen — every outcome is logged at a severity-matched level and never blocks the HTTP server from starting.
- Added `ENV DOCKTOR_DB_AUTO_PUSH=true` to the `Dockerfile`'s final stage and confirmed by inspecting the actual built image (not by assumption) that `node_modules/.bin/prisma` and `server/prisma/{prisma.config.ts,schema/}` are present at exactly the paths the module resolves — no new `COPY` was needed, the existing `server/prisma` copy already covers it.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Task 3's literal `<verify>` command omits the Docker socket mount, which crashes cold start for an unrelated, pre-existing reason**
- **Found during:** Task 3, first live cold-start attempt
- **Issue:** Running the built image exactly as the plan's `<verify>` command specifies (no `-v /var/run/docker.sock:/var/run/docker.sock`) causes `StatePoller.start()` (called from `startJobs()` in `app.ts`'s `onReady` hook) to hang inside `dockerode`'s `getEvents()` call against a socket that doesn't exist in the container. Each individual job's `start()` is wrapped in a try/catch (Phase 02 precedent), but a *hang* — as opposed to a rejection — is not caught by that guard; Fastify's own `onReady` hook timeout (`FST_ERR_HOOK_TIMEOUT`) eventually fires and the process exits(1). Confirmed reproducible with `DOCKTOR_DB_AUTO_PUSH=false` too, so it is unrelated to schema-sync itself.
- **Fix:** Added `-v /var/run/docker.sock:/var/run/docker.sock` to the live-verification `docker run` commands, matching `docker-compose.yml`'s real deployment mount (`/var/run/docker.sock:/var/run/docker.sock`, confirmed present there). No application code was changed — this is a gap in the plan's literal test harness command, not a defect in `schema-sync.ts`/`index.ts`/`Dockerfile`.
- **Files modified:** None (test-harness command only, not committed).
- **Verification:** With the socket mounted, the container stayed up and produced the expected `[schema-sync]` log lines instead of crashing within seconds.
- **Note for future test authors / 05.1-07 (deployment docs):** any live-container verification of this image must mount the Docker socket, or `StatePoller`'s job-startup hang will crash the container for reasons unrelated to whatever is actually being tested. This is worth calling out explicitly in deployment documentation as a required mount, which `docker-compose.yml` already has correct — only ad-hoc `docker run` test harnesses (like this plan's `<verify>` command) can omit it.

## Known Limitation (NOT a deviation — see key-decisions above)

**Task 3's live `GET /api/setup/status` -> 200 proof against a never-initialised database could not be produced in this execution session.**

This session's Bash tool environment cannot receive a TCP payload from any port published by a Docker container, even though the TCP three-way handshake completes instantly. This was root-caused independently in this session with three separate probes, going beyond what was strictly necessary to confirm it matches 05.1-01's prior finding:

1. `bash`'s `/dev/tcp/127.0.0.1/55432` — connects instantly.
2. `docker run --rm --network host postgres:18 psql "postgresql://docktor:docktor@127.0.0.1:55432/docktor" -c "SELECT 1;"` — hung indefinitely (killed after 8s of no response) despite the throwaway Postgres container being confirmed healthy via `pg_isready` moments earlier.
3. A raw Python `socket.create_connection` directly from the **host shell** (not inside any container) to `127.0.0.1:55432` connects immediately, but `recv()` times out after 5s with zero bytes received. The identical test against `127.0.0.1:3000` — the Docktor app's **own** HTTP port, nothing to do with Postgres — produced the exact same symptom: instant TCP connect, then a `recv()` timeout with zero bytes.

That last result is the most important new data point beyond what 05.1-01 established: the block is not Postgres-specific or wire-protocol-specific, it affects **any** Docker-published port's payload delivery in this sandboxed session. No code change in this repository can fix a host-level TCP data-path failure to Docker-published ports — this matches 05.1-01's own conclusion (`server/prisma/prisma.config.ts` and this plan's `schema-sync.ts` were, correspondingly, not modified in response to this).

**What WAS verified live, despite this:**
- The `unreachable` outcome: the app container was left running against the (network-blocked) Postgres container. `syncDatabaseSchema()`'s reachability guard correctly retried for its full bounded budget (~1 minute wall time, consistent with 6 attempts × up to 5s connect timeout + 5 × 5s retry delay), logged `[schema-sync] database unreachable at 127.0.0.1:55432 after retry budget exhausted` (host:port only, never the password-bearing `DATABASE_URL`), and — critically — the container **stayed running** afterward instead of crashing, proving T-05.1-22's mitigation (a failing schema step must not take down the whole process) end-to-end in a real container.
- The `skipped` outcome: with `DOCKTOR_DB_AUTO_PUSH=false` set, the log showed only `[schema-sync] skipped (DOCKTOR_DB_AUTO_PUSH=false)` with zero mentions of `prisma`, `db push`, `applied`, or `already-current` anywhere in the container's output — confirming no CLI was ever spawned.
- Everything static: `tsc --noEmit` clean, `docker build` succeeds, and the built image contains the Prisma CLI plus `server/prisma/` at exactly the paths `schema-sync.ts` resolves (Task 2's own acceptance criteria, independently re-confirmed).

**What was NOT verified:** the `applied` outcome (push against a genuinely empty schema), the `already-current` outcome on a second start, the `GET /api/setup/status` 200 response with `setupComplete`, and the requested "measured added startup latency of the schema step on the already-current run" — none of these are reachable without a working payload-level connection to the app's own HTTP port, which this session does not have.

**Action required:** a human (or an execution environment without this restriction) must run Task 3's exact sequence — a throwaway `postgres:18` container on a collision-proof host port, the built image on `--network host` **with `/var/run/docker.sock` mounted** (see Deviations above), polling `GET /api/setup/status` — to close out this plan's D3 coverage item. If it fails there, the investigation should start from the schema-sync module's own logs (already structured for this: every outcome is logged with a clear label), not from re-litigating the environmental question already answered twice now (05.1-01 and this plan).

**Cleanup performed:** both throwaway containers (`docktor-cold-db`, `docktor-cold-app`) and both throwaway images (`docktor-schema-check`, `docktor-cold-app-img`) were removed at the end of this session; confirmed via `docker ps -a` and `docker images` that none remain.
