<objective>
Close gap **G-05.1-1**: `yarn workspace @docktor/server test:integration` fails on a native Windows host with `Caused by: Error: spawnSync C:\Users\...\node_modules\.bin\prisma ENOENT`, while passing in CI. The cause is a genuine cross-platform code defect, not a local environment problem — an unstated POSIX assumption baked into a hardcoded CLI path, with zero CI coverage because CI runs only on `ubuntu-latest`.

Purpose: a contributor on Windows currently cannot run the integration suite at all. Worse, the identical resolution defect exists a second time in production boot code (`server/src/lib/schema-sync.ts`), where its failure mode is *silent*: `syncDatabaseSchema()` catches everything, logs a `failed` outcome, and starts the server anyway — so a Windows `yarn dev` run gets an unapplied schema with no obvious cause. Both call sites are fixed here, from one shared resolver, so the defect class is closed rather than relocated.

Output: a new `server/src/lib/prisma-cli.ts` resolver with unit coverage, and both call sites rewired to launch the CLI through Node's own binary.

The architecture here is already proven and shipped; this is a surgical correction to one resolution step inside two existing, working call paths. A thin vertical slice would add no information that Task 1's end-to-end executability proof does not already give. Do not restructure either call path beyond the resolution change.

**Out of scope:** switching the schema workflow to `prisma migrate` (already tracked separately), changing what arguments either call site passes, and adding Windows to the CI matrix (worth doing, but it is a separate infrastructure change — record it as a pending todo in Task 3 rather than doing it here).

  <name>Task 1: Add a platform-independent Prisma CLI resolver</name>
  <files>server/src/lib/prisma-cli.ts, server/test/unit/lib/prisma-cli.test.ts</files>
  <behavior>
    - Returns an absolute path to a file that exists on disk.
    - The returned path equals the `bin.prisma` target declared by the *installed* prisma package's own `package.json` (read at test time via module resolution of `prisma/package.json`, joined onto that package's directory) — never a hardcoded literal, so a future prisma release that relocates its entrypoint fails this test loudly instead of silently.
    - Spawning `process.execPath` with the returned path plus `--version` exits 0 and prints a line whose first token is `prisma` — this is the exact invocation form both call sites will use, so it proves executability end-to-end rather than just proving a string was produced.
    - Resolution is independent of `process.cwd()`: the same value comes back after `process.chdir(os.tmpdir())` as before it (restore the original cwd in a `finally`).
  </behavior>
  <action>
    Create `server/src/lib/prisma-cli.ts` exporting one function, `resolvePrismaCliEntrypoint(): string`.

    Implement it with `createRequire` from `node:module`, bound once at module scope to `import.meta.url` (name the binding `moduleRequire`, not `require`, to avoid shadowing confusion in an ESM file), resolving the specifier `prisma/build/index.js`. That subpath is declared in the installed prisma package's own `exports` map (verified against the pinned 7.4.0 in this repository), so it is supported public resolution rather than reaching into package internals. Anchoring on `import.meta.url` rather than `process.cwd()` is what makes one implementation correct in all three layouts this repository runs in: vitest resolving from `server/src/lib`, `tsx` running from source, and the built image where the compiled module sits at `/app/dist/server/lib` and the lookup walks up to the `/app/node_modules` tree the Dockerfile copies in.

    Wrap the resolution in `try`/`catch` and rethrow a new `Error` that names the specifier that failed to resolve and states that the dependency install is missing or incomplete, preserving the original via `cause`. Without this, a broken install surfaces as a bare module-not-found thrown from deep inside a vitest hook, which is exactly the kind of misleading symptom this gap already cost a debugging session on.

    Write a doc comment on the exported function stating WHY this exists, because the next person to touch it will otherwise "simplify" it back into the bug:
    - Package managers using the node-modules linker generate, on POSIX, a symlink to a shebang-prefixed JS file, which the kernel execs transparently; on native Windows the same convention instead generates cmd/PowerShell shim files, so an extensionless path into that generated directory is not launchable by Windows' native process creation. That divergence is what produced the reported ENOENT.
    - Node's own binary is a real executable on every platform, so handing it the resolved JS entrypoint removes the divergence entirely, with no shell and no platform branch.
    - State the caller contract explicitly: callers MUST invoke this as `execFile(process.execPath, [resolvePrismaCliEntrypoint(), ...argv])` and MUST NOT add a shell option — passing the CLI path as a shell-interpolated string would reopen the metacharacter-injection risk that T-05.1-02 and T-05.1-24 were written to close.

    Create `server/test/unit/lib/prisma-cli.test.ts` covering the four behaviors above. Follow the existing conventions in `server/test/unit/lib/` (vitest `describe`/`it`, import the module under test through the `../../../src/...` relative path the vitest alias handles). The `--version` spawn takes roughly ten seconds on a cold start, which exceeds vitest's default 5s per-test timeout and the `unit` project sets no override — pass an explicit per-test timeout of `30_000` as the third argument to that `it(...)` call, or it will fail for a reason that has nothing to do with the code.
  </action>
  <verify>
    <automated>yarn workspace @docktor/server test:unit test/unit/lib/prisma-cli.test.ts</automated>
  </verify>
  <done>`resolvePrismaCliEntrypoint()` returns an absolute, existing path matching the installed prisma package's declared bin target, and `process.execPath` can execute that path directly and print a prisma version. All four unit tests pass.</done>
