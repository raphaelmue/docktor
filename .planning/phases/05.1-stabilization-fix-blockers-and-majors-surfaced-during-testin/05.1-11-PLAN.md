<objective>
Close gap **G-05.1-3**: on a Windows host running Docker Desktop, with default settings and a cleanly booted server, the managed stacks directory does not exist inside the container. There is no error — it is a silent absence.

The application never creates its own top-level stacks directory. `server/src/index.ts` asserts the host and container paths match but never touches the filesystem; `server/src/lib/stacks-dir.ts` is pure path-string helpers; and the only `mkdir` in the codebase (`stack-filesystem.ts`'s `createDirectory()`) is scoped to per-stack subdirectories created on demand. The directory's existence therefore rests entirely on Docker auto-creating a missing short-syntax bind-mount source — behavior Docker documents as legacy and best-effort, and which Docker Desktop's WSL2 integration handles through a materially different code path than native Linux dockerd for a bare Linux absolute path that maps to no real host location. This codebase already independently depends on that same Desktop-vs-Linux divergence being real elsewhere: the Dockerfile forces filesystem polling because Desktop's virtualized bind mounts do not propagate inotify events.

Purpose: make directory existence an application-owned guarantee on every platform rather than an unstated dependency on unspecified container-runtime behavior. This gap reproduces with byte-identical, mismatch-free default settings and is independent of G-05.1-2.

Output: an `ensureStacksDir()` helper with unit coverage, wired into the startup sequence.

**Design note — where the code goes.** The diagnosis proposes an inline `fs.mkdir` in `server/src/index.ts`. Put the logic in `lib/stacks-dir.ts` as an exported `ensureStacksDir()` and call that from `index.ts` instead. Same behavior and same startup position, but it keeps directory concerns in the module that already owns stacks-path resolution, keeps `index.ts` a thin sequence, and makes the behavior reachable from `server/test/unit/lib/stacks-dir.test.ts` — `index.ts` is top-level side-effect module code and cannot be unit tested.

**Deliberately out of scope**, recorded as a todo in Task 2 rather than built here: `mkdir` alone cannot distinguish "the bind mount attached and this is a no-op" from "the mount never attached, so this just created a directory in the container's own writable layer that will vanish on recreation." The diagnosis assessed that as a distinct, more severe failure mode needing its own mount-point check, and explicitly not a blocker for this gap, whose stated truth is satisfied by the directory existing.

**Decomposition shape:** horizontal, not tracer-first (`--no-tracer` reasoning) — one new function inside a proven startup path. Task 2 carries a real end-to-end boot proof.
</objective>

| T-05.1-50 | Tampering | `ensureStacksDir()`'s creation target | medium | mitigate | The path comes only from `getStacksDir()`, which resolves a single operator-controlled env var through `path.resolve` — never from request data.
