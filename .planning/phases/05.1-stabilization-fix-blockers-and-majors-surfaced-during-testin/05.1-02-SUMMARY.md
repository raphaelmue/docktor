# Phase 05.1 Plan 02: SSE broadcasts for manual stack actions and env config-changed Summary

**StackService now publishes `stack_status`/`config_changed` SSE events on every manual action and config write, closing the two observability gaps (todos M3/M5a) where the UI showed nothing during a deploy/stop/restart/update and env-only edits never flagged the config-changed banner.**

- **Tasks:** 3

## Accomplishments

- Every `StackService` status transition (deploy, stop, restart, updateImages, upgradeServiceImage — including the ERROR paths and the identical-from/to restart case) now broadcasts `stack_status` over SSE immediately after the DB write, via a single private `transitionStatus()` wrapper that is now the sole caller of `repo.transitionStatus()`
- A throwing SSE subscriber can no longer strand a stack in a transitional status — both the new `transitionStatus()` and `publishConfigChanged()` wrappers catch and log broadcaster failures rather than propagating them
- `updateStack()`'s env branch now flags `Stack.configChanged` and publishes `config_changed`, matching the compose branch's existing behaviour; `lastKnownHash` stays compose-only (never written by the env branch)
- The stack detail page (`[id].tsx`) now calls `refetch()` after a successful compose or env save, so the "Configuration has changed" banner appears immediately on the saving tab with no manual reload; a failed save intentionally skips the refetch, leaving the editor and dirty flag untouched

## Decisions Made

- Application service publishes (not the repository) — see `key-decisions` in frontmatter for full rationale.
- Broadcaster failures are non-fatal by design (caught + logged), matching the plan's threat register mitigation for T-05.1-06 (DoS via a throwing SSE subscriber).
- Env-only `config_changed` events reuse the stack's current `lastKnownHash` (or `""`) rather than inventing a separate env hash — every consumer only keys off `stackId`.
- Task 3 was tested at both the page level and the hook level (see coverage D5) rather than only the hook-level fallback the plan offered, since the page turned out to be testable in isolation by mocking its child components (following the existing `backup-detail-page.test.tsx`/`service-upgrade-dialog.test.tsx` pattern in this codebase) — this gives direct coverage of the actual call-site sequencing (`refetch()` reached only after a successful `updateStack()`) rather than only the downstream mechanism.
- Test timeouts for the new page-level test were bumped to 15s (from vitest's 5s default): under this host's full-parallel-test-suite CPU contention (the same class of flake documented for Playwright in `05.1-01-SUMMARY.md`/`STATE.md`), the 5s default flaked even though the tests pass reliably in isolation or in small groups.
