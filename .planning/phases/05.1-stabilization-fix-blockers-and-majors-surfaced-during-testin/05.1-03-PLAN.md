<objective>
Fix the Docker-outside-of-Docker bind-mount path mismatch that silently writes every managed stack's relative-volume data to the wrong host location (todo item B3), and replace the 3-year-old OS-packaged restic with an explicitly pinned, checksum-verified binary (todo item N1).

Purpose: B3 is a data-integrity blocker. Docktor talks to the *host's* Docker daemon, but the shipped compose file remaps the host stacks directory to a different container path. `docker compose` running inside the Docktor container resolves `./volumes/data` against its own view, producing `/stacks/<id>/volumes/data`, and sends that absolute string to the host daemon — which has no such directory and creates a stray top-level one. The container starts fine, so nothing surfaces the problem. It very likely also makes backups near-empty, because restic runs inside the Docktor container and archives the path *Docktor* sees, not the path the data actually landed on.
Output: a compose file and image whose stacks path is identical on both sides, a startup assertion that refuses to run a mismatched deployment, and a pinned restic.

This plan owns `Dockerfile` and `docker-compose.yml` for wave 1. Plan 05.1-04 (startup schema sync) and plan 05.1-07 (deployment docs) both build on the files this plan leaves behind and run in later waves.
</objective>

  <context>
Fixing the DooD bind-mount bug requires the stacks directory to be mounted at the same absolute path on the host and inside the Docktor container. That is a one-way change for any existing install: `Stack.hostPath` rows hold absolute paths built from the old value and `FileWatcher.findStackByPath()` matches them exactly, so stale rows silently stop reacting to file changes; and stack data already on disk does not move itself.

Two sub-decisions are settled by the proposals below unless you say otherwise, and the third is the real choice:

Canonical default path — proposal `/opt/docktor/stacks` on both sides. It matches the example already written into `server/prisma/schema/stack.prisma` (`/opt/docktor/stacks/my-nextcloud`) and is a conventional self-hosted location.

How the variable is configured — Phase 02 plan 08 deliberately moved `DOCKTOR_STACKS_DIR` out of compose `environment:` into a fixed Dockerfile `ENV`, reasoning that it names a container-internal mount point that never varies per deployment. This fix invalidates that reasoning: the container path must now equal whatever host path the operator chose, so it is deployment-varying again. Proposal: keep a Dockerfile `ENV` default and have the compose file drive both sides of the volume plus the env var from one variable, so they cannot drift apart.

The third question — what happens to existing installs — is the options below. Your own deployment is the only known install, so answer with that in mind.
  </context>
  <options>
    <option id="rebase">
      <name>Automatic hostPath rebase on startup</name>
      <pros>Removes the one-way-ness for the database: any `Stack.hostPath` not under the current `getStacksDir()` is rewritten to point at the new root, so the watcher and the backup path keep working. Cheap to implement as a single repository method. A loud startup log names exactly which rows were rewritten.</pros>
      <cons>Does not move files on disk — the operator still has to relocate the stacks directory themselves, and a rebased row pointing at a directory that was never moved is wrong in a new way until they do. Adds a startup write path that touches every stack row.</cons>
    </option>
    <option id="no-rebase">
      <name>No rebase; document the manual migration</name>
      <pros>No startup write path and no chance of silently rewriting rows the operator did not expect. The failure is loud and obvious: a mismatched path fails the startup assertion and the operator fixes it deliberately.</pros>
      <cons>Any existing install must move its stacks directory and reconfigure by hand before Docktor will start again. More friction for the one known deployment.</cons>
    </option>
  </options>
  <resume-signal>Reply with `rebase` or `no-rebase`, plus a different canonical path or configuration mechanism if you do not want the proposals above.</resume-signal>
</task>

    The final image stage currently obtains restic from the base image's package repository, which on `node:22-slim` (Debian bookworm) pins it to 0.14.0 from October 2022. Replace that with a direct, explicitly pinned binary download in the same layer style already used for the Docker CLI and the compose plugin.

    Determine the current stable restic release from the project's GitHub releases page and pin that exact version literally — never `latest`, so builds stay reproducible. Download the `restic_<version>_linux_amd64.bz2` asset, verify it against the checksum published in that release's `SHA256SUMS` file before decompressing (do not skip this — an unverified binary download into a container that holds the host Docker socket is a supply-chain foothold), decompress it, `chmod +x`, and place it on `PATH` at `/usr/local/bin/restic`. The whole download-verify-install sequence must be a single `RUN` so a failed verification cannot leave a usable layer behind. Leave `ca-certificates` and `curl` in the package-manager layer — the download needs both — and remove only the restic package from it.

    Record the pinned version in the SUMMARY, and note in the same place that this pin needs periodic manual review since nothing automatically bumps it.

    Do not change `server/src/infrastructure/restic-executor.ts` — resolving `restic` from `PATH` continues to work, and `RESTIC_BINARY` remains available as an override.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Docktor container -> host Docker daemon | `/var/run/docker.sock` is bind-mounted; anything Docktor asks the daemon to do runs with host root authority |
| managed stack compose file -> host filesystem | volume declarations in a user-authored compose file become host paths the daemon creates and binds |
| Docktor container -> host root filesystem | `docker-compose.yml` mounts `/:/host:ro` for brownfield scanning |
| image build -> internet | the final stage downloads the Docker CLI, the compose plugin, and (after this plan) restic from remote URLs |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05.1-09 | Tampering | relative bind-mount resolution in `DockerExecutor.composeExec` under DooD | high | mitigate | Task 2: identical host and container stacks paths, so a relative volume resolves to the same string on both sides. Today a managed stack silently causes the host daemon to create and write to arbitrary top-level host directories such as `/stacks/<id>/...` outside any Docktor-managed tree |
| T-05.1-10 | Denial of Service / data loss | backups archiving a different physical path than the containers write to | high | mitigate | Task 2 requires explicit confirmation that `stack.hostPath` (restic's `stackPath`) and the containers' bind-mount source now resolve to the same host location. A silently near-empty backup is indistinguishable from a good one until a restore is attempted |
| T-05.1-11 | Elevation of Privilege | `getStackPath(id)` composing a host path from a stack id | medium | mitigate | Stack ids are `slugify()`d at creation in `StackService.createStack`, which is what keeps `..` out of the joined path. | T-05.1-12 | Tampering (supply chain) | restic binary downloaded from a remote URL into an image holding the host Docker socket | high | mitigate | Task 3: pin an explicit version, verify the asset against the release's published `SHA256SUMS` in the same `RUN` before it becomes executable.
