## Fixed Issues

### CR-01: `initiateRestore()` never validates the stack's current status before transitioning to RESTORING

**Files modified:** `server/src/application/backup-service.ts`, `server/src/domain/stack-status-machine.ts`
**Commit:** `ecc7f4a`
**Applied fix:** Added `assertTransition(stack.status, "RESTORE")` to `initiateRestore()`, mirroring `initiateBackup()`'s existing guard. The `RESTORE` action was already modeled in `TRANSITIONS` but scoped to `["STOPPED", "ERROR"]` only — too narrow to allow restoring the common case of a `RUNNING`/`HEALTHY`/`UNHEALTHY` stack (the default status in the test fixtures, and the realistic case an operator would restore from), since `runRestoreProcess()` already calls `docker.stop()` itself before restoring. Widened it to `["RUNNING", "HEALTHY", "UNHEALTHY", "STOPPED", "ERROR"]`, mirroring `BACKUP`'s allowed-from list, while still blocking transitional states (`DEPLOYING`, `UPDATING`, `BACKING_UP`, `RESTORING`, `DRAFT`) — the exact race the finding described. Verified against the full unit suite (`backup-service.test.ts`, `stack-status-machine.test.ts`) and `tsc --noEmit`.

### WR-01: Stack-detail breadcrumb link uses a query string the router doesn't consume

**Files modified:** `client/src/routes/app/stacks/[id].tsx`, `client/test/integration/stacks.spec.ts`
**Commit:** `fb38034`
**Applied fix:** Changed the breadcrumb `Link` to build a path segment (`/stacks/${id}/${activeTab}`) instead of a query string, matching the registered route (`path="/stacks/:id/:tab?"`) and the existing in-page `navigate()` tab-switch call. Added a Playwright regression test that navigates to a non-Overview tab (`/stacks/my-app/compose`), asserts the breadcrumb link's `href`, clicks it, and confirms the tab is preserved — the existing test only covered the Overview case, where the bug was invisible.

### WR-02: `backupStackRepo.update` bypasses the repository layer and uses an unjustified `as` cast

**Files modified:** `server/src/application/index.ts`, `server/src/repositories/stack-repository.ts`
**Commit:** `6244791`
**Applied fix:** Added `StackRepository.updateStatusFields()` — a narrow `{status, previousStatus?}` write, kept distinct from the existing `updateStackStatus()` (which also short-circuits on unchanged status and writes a `statusLog`, neither wanted by `BackupService.writeStackStatus()`). The `BackupStackRepo` adapter in `application/index.ts` now calls this repository method instead of importing `prisma` directly. The remaining `as` cast is now a real runtime narrowing (only `status`/`previousStatus` are destructured off the wider input before being passed on) with a comment explaining why, per CLAUDE.md's "no unchecked casts without justification" rule.

### WR-03: Docker CLI / Compose plugin installed without checksum verification

**Files modified:** `Dockerfile`
**Commit:** `7d60b44`
**Applied fix:** Both downloads are now checksum-verified before use, mirroring the restic-install stage. `docker/compose` publishes a `checksums.txt` per release — verified against that via `sha256sum -c`. `download.docker.com` does not publish a checksum manifest for the static CLI tarball, so the sha256 of the exact `docker-27.5.1.tgz` artifact was computed and pinned directly in the Dockerfile (documented in an inline comment, with instructions to recompute on version bumps). Verified by extracting the new `RUN` step into a standalone Dockerfile and running `docker build` end-to-end: both `sha256sum -c` checks reported `OK` and the resulting `docker`/`docker-compose` binaries ran successfully.

### WR-04: Hardcoded, weak default Postgres password shipped in `docker-compose.yml`

**Files modified:** `docker-compose.yml`, `docs/deployment.md`
**Commit:** `d13afcf`
**Applied fix:** Removed the hardcoded `POSTGRES_PASSWORD: docktor` default; the `db` service now reads it via `env_file: .env.local` (the same file `docktor`'s `DATABASE_URL` already comes from) instead. Note: the review's suggested `${VAR:?...}` top-level compose-interpolation syntax was tested and found to **not** work here — `docker compose`'s top-level `${VAR}` substitution only reads a literal `.env` file (or the real process environment), never `.env.local`; only the service-level `env_file:` directive reads `.env.local`. Verified end-to-end with a standalone `docker compose` stack: with `POSTGRES_PASSWORD` unset, the official `postgres:18` image now refuses to start (`Database is uninitialized and superuser password is not specified...`) instead of silently running with a guessable default; with it set, the container starts and passes its healthcheck. Updated `docs/deployment.md`'s quickstart step and environment-variable reference table to document the new required variable. `.env.example`/`.env.production` were **not** modified — both are excluded from this fixer's file access by filesystem permission settings (same restriction noted in `05.1-REVIEW.md`'s frontmatter); an operator following the updated `docs/deployment.md` will still need to add `POSTGRES_PASSWORD=<same password as DATABASE_URL>` to `.env.local` manually since it is not present in the template.

### WR-05: `runRestoreProcess()` silently continues with an empty env object when the backup repository is unconfigured

**Files modified:** `server/src/application/backup-service.ts`, `server/test/unit/application/backup-service.test.ts`
**Commit:** `84d3b0a`
**Applied fix:** `runRestoreProcess()` now re-checks `getBackupRepoConfig()` and throws the same `BadRequestError` message `initiateRestore()` uses if it comes back null, instead of falling back to `{}` and letting restic produce an opaque error. Because the existing `runRestoreProcess()`/log-buffer-parity unit tests relied on `mockSettingsService.getMany` being unmocked (implicitly exercising the now-fixed empty-env fallback), they were updated to explicitly configure a backup repository (mirroring `initiateRestore()`'s existing pattern), and a new regression test was added asserting the unconfigured-repo path fails fast without calling `resticExecutor.run` and follows the normal FAILED/ERROR handling. Full `backup-service.test.ts` suite passes (86 tests, up from 75, all green).
