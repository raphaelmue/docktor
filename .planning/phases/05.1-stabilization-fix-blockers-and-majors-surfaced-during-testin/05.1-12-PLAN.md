<objective>
Close gap **G-05.1-4**: on a native Windows host, `POST /api/stacks/import/scan` returns stack paths separated by forward slashes (`C:/Users/.../docktor-imports-test-6oKgpG`) while the Windows client's own representation of that same directory uses backslashes (`C:\Users\...\docktor-imports-test-6oKgpG`). The two strings name the same directory but are not equal, so `server/test/integration/imports.test.ts:108` fails and any Windows consumer comparing a returned path against a locally-derived one sees a spurious mismatch.

The mechanism is fully diagnosed. `server/src/infrastructure/brownfield-scanner.ts`'s `scan()` calls `fg(..., {absolute: true})`, and fast-glob's `EntryTransformer` runs `utils.path.unixify()` on every absolute result unconditionally on every platform — that is fast-glob's documented, intentional design, since glob patterns are POSIX-delimited by convention. The scanner then assigns `path: filePath` verbatim and `directory: path.dirname(filePath)`. Critically, `path.win32.dirname()` does not renormalize separator style; it only slices at the last separator it finds, so it preserves the forward slashes already present. Nothing downstream corrects this: both scan routes return the `ScanResult` object verbatim for Fastify to serialize.

Purpose: make the scanner's output honour the host OS's path conventions, so the one place that consumes a deliberately-POSIX-ised third-party output converts it back at the boundary instead of leaking a foreign representation through the API.

Output: a one-expression normalization at the fast-glob boundary, a Windows-shaped regression test that runs on Linux, and a separator-agnostic client helper so no consumer regresses.

**Design note — normalize at the boundary, before dedup.** The diagnosis suggests normalizing `filePath` and `path.dirname(filePath)` at the point of use (lines 103-104). Normalize one step earlier instead: map fast-glob's returned array through `path.normalize()` as it is pushed into `foundFiles` (line 78). Same result for both fields from a single call, and it additionally makes the `new Set(foundFiles)` dedup on line 93 operate on the canonical spelling — two overlapping scan directories that produce different spellings of one file now collapse correctly rather than yielding a duplicated stack.

**Deliberately out of scope — do not normalize `absolutePaths`.** `DiscoveredStack.absolutePaths` comes from `ComposeAnalyzer` parsing bind-mount strings out of the operator's compose YAML, not from fast-glob. Those strings are author-written content that `migration-service.ts` later matches against as `originalPath`; rewriting their representation is a different change with a different risk profile and is not part of this gap. Task 2 makes the client *read* them tolerantly, which is safe, but the values themselves must pass through the server untouched.

**Decomposition shape:** horizontal, not tracer-first. This is a single-defect gap closure on an already-proven path — one expression in a server adapter plus the client consumers that expression affects. A thin vertical slice would add no information the diagnosis has not already established end-to-end. Both tasks are TDD: each starts from a test that is red against current `main`.

**Verified during planning (do not re-derive):** the `node:path`-mocked test approach in Task 1 was empirically confirmed against this repo before this plan was written. It reproduces the exact Windows failure on Linux (red), the one-line normalization turns it green, and all 15 pre-existing `brownfield-scanner.test.ts` cases still pass unchanged.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| filesystem -> scan API response | Operator-supplied scan roots are globbed and the resulting absolute paths are serialized into an authenticated HTTP response |
| scan API response -> client-derived display name | A server-returned path string is parsed by the client to produce a name that is then sent back as a stack display name |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05.1-54 | Information Disclosure | `BrownfieldScanner.scan()` output | low | accept | Normalization changes only the separator characters of paths the scan already returned; it exposes no path that was not already in the response. Both scan routes remain gated — `/api/stacks/import/scan` by the plugin-wide `requireAuth` hook, `/api/setup/scan` by the wizard-completion gate — and neither gate is touched. |
| T-05.1-55 | Tampering | `path.normalize()` on glob output | low | mitigate | `normalize` collapses `.` and `..` segments, which is a canonicalization applied to paths fast-glob already resolved to absolute form. It cannot introduce a segment, and it runs before the dedup rather than before any filesystem access, so it cannot widen what is read. The `SYSTEM_DIRS` filter it sits downstream of is unchanged and still evaluates operator input on the way in. |
| T-05.1-56 | Spoofing | client display-name derivation | low | mitigate | `directoryDisplayName()` returns a single trailing path segment containing no separator of either style, so a crafted directory name cannot smuggle a path into the display name. The value remains untrusted downstream: the adopt route re-derives the stack id via `slugify()`, which is the existing containment guarantee and is not modified. |
| T-05.1-57 | Denial of Service | `directoryDisplayName()` | low | accept | A single split-and-filter over a bounded path string, with no regular-expression backtracking and no recursion. |
| T-05.1-SC | Tampering | npm/pip/cargo installs | high | mitigate | Not applicable — this plan adds no dependency. `node:path` is a Node built-in and the client helper imports nothing. No package-legitimacy checkpoint required. |
</threat_model>
