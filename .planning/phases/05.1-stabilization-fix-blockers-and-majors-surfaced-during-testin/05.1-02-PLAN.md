<objective>
Close two observability gaps reported during Phase 1-5 testing (todo items M3 and M5a): manual stack actions never broadcast an SSE status update, so the UI shows nothing while a deploy/stop/restart/update is in flight; and saving the env file through the app never flags the stack as config-changed, unlike saving the compose file.

Purpose: without these, the entire real-time status story is a lie for exactly the operations a user performs deliberately — only the 60s poller broadcasts, and it unconditionally skips the transitional statuses a manual action just set.
Output: `StackService` publishes `stack_status` at every status transition and `config_changed` on every config write; the stack detail page refetches after a successful save.

Scope boundary: this plan owns `server/src/application/stack-service.ts` only. The identical SSE gap in `BackupService`'s backup/restore transitions is covered by plan 05.1-04, which owns `backup-service.ts`. The `FileWatcher` half of M5 (watching `.env` for external edits) is covered by plan 05.1-06, which owns `file-watcher.ts`.
</objective>

    - `deployStack` on a RUNNING stack emits a `stack_status` event with `stackStatus: "DEPLOYING"` before the docker call, and a second with `"RUNNING"` after it succeeds
    - `deployStack` whose docker call fails emits `"DEPLOYING"` then `"ERROR"`
    - `stopStack` emits `"STOPPED"`; a failing `docker stop` then emits `"ERROR"`
    - `restartStack` emits an event even when the from-status and to-status are identical
    - `updateImages` emits `"UPDATING"` then `"RUNNING"`, or `"UPDATING"` then `"ERROR"` on failure
    - `upgradeServiceImage` emits `"UPDATING"` then `"RUNNING"`/`"ERROR"`, and emits nothing on the idempotent no-op path where the target tag already matches

  </behavior>
  <action>
    Locked design decision, to be recorded in the SUMMARY: the **application service** publishes, not the repository. `StackRepository` is data access and has no broadcaster dependency; adding one would put an I/O side effect behind a Prisma write and break the layering rule that repositories are the only place that touches Prisma and nothing else. This also matches the existing convention in `state-poller.ts` and `file-watcher.ts`.

    Add a fifth constructor parameter to `StackService`, `broadcaster: Pick<StateBroadcaster, "publish">`, declared with the same structural-`Pick` narrowing `FileWatcher` uses so the service stays unit-testable with a plain object. Add a private method `transitionStatus(id, from, to, message?)` on `StackService` that awaits `this.repo.transitionStatus(id, from, to, message)` and then calls `this.broadcaster.publish({type: "stack_status", stackId: id, stackStatus: to})`. Replace every direct `this.repo.transitionStatus(...)` call in `stack-service.ts` with a call to that private method — there are call sites in `deployStack` (three), `stopStack` (two), `restartStack` (one), `updateImages` (three) and `upgradeServiceImage` (four); verify the exact count against the file rather than trusting this list.

    The publish must happen after the DB write resolves, never before — a broadcast that precedes a failed write would advertise a status that does not exist. The publish must not be able to fail the transition: if `publish` throws, catch it, log with a `[StackService]` prefix, and continue, because a subscriber's exception must not strand the stack in a transitional status (this is the same wedging hazard the existing comments in `deployStack`/`updateImages` describe).

    Update `server/src/application/index.ts` to pass the existing imported `stateEventBroadcaster` singleton as the new fifth argument. Update the construction at `server/test/unit/application/stack-service.test.ts` to pass a mock with a `publish` spy.

    Write the tests first: extend `server/test/unit/application/stack-service.test.ts` with assertions for each behaviour listed above, confirm they fail, then implement.
  </action>

  <behavior>
    - `updateStack(id, {envContent: "FOO=bar"})` calls `setConfigChanged(id, true)` and publishes a `config_changed` event for that stack
    - `updateStack(id, {envContent: ""})` removes the env file and still calls `setConfigChanged(id, true)` and publishes — deleting configuration is a configuration change
    - `updateStack(id, {composeContent})` whose hash differs from `lastKnownHash` publishes a `config_changed` event carrying the new hash
    - `updateStack(id, {composeContent})` whose hash equals `lastKnownHash` calls `setConfigChanged(id, false)` and publishes nothing
    - `updateStack(id, {displayName})` alone touches neither `configChanged` nor the broadcaster
  </behavior>
  <action>
    In `StackService.updateStack()`, extend the `envContent` branch: after `this.fs.writeEnv(id, input.envContent)` or `this.fs.removeEnv(id)` succeeds, call `await this.repo.setConfigChanged(id, true)`. Do not hash the env content and do not write it to `Stack.lastKnownHash` — that column holds the SHA256 of `docker-compose.yml` and is the sole input to `FileWatcher`'s change detection; putting an env hash there would make every subsequent compose comparison wrong. Unconditional flagging is the intended semantics here per the todo's own solution note.

    In the same method, publish `config_changed` through the broadcaster added in Task 1, matching the shape `file-watcher.ts` already publishes: `{type: "config_changed", stackId: id, newHash}`. For the compose branch use the freshly computed `composeConfig.hash`, and publish only when the hash actually differs from `stack.lastKnownHash` (a same-hash save sets `configChanged` to false and must not announce a change). For the env branch there is no compose hash to report — reuse the stack's current `lastKnownHash` (or the empty string when it is null) so the event shape stays uniform and consumers, which only key off `stackId`, behave identically. Record that choice in the SUMMARY.

    Wrap the publish in the same non-throwing guard used in Task 1.

    Write the tests first in `server/test/unit/application/stack-service.test.ts` covering every case in `<behavior>`, confirm they fail, then implement.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server -> every subscribed SSE client | `stateEventBroadcaster.publish` fans out to every open `/api/events` connection; anything put into an event reaches every authenticated session |
| authenticated client -> `PUT /api/stacks/:id` | compose and env file contents cross into the server filesystem here |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05.1-05 | Information Disclosure | new `stack_status` / `config_changed` publishes in `StackService` | low | mitigate | Publish only the fields the existing `StackStatusEvent` / `ConfigChangedEvent` interfaces declare — stack id, status, compose hash. Never widen an event to carry compose content, env content, or an error string from a file write, since env files hold credentials and every subscriber receives every event |
| T-05.1-06 | Denial of Service | a throwing SSE subscriber inside `transitionStatus` | high | mitigate | Task 1 wraps every `publish` in a non-throwing guard. Without it a subscriber exception propagates out of the transition and strands the stack in DEPLOYING/UPDATING, which no action's allowed-from list accepts and `StatePoller` unconditionally skips — an unrecoverable wedge reachable by any authenticated user pressing Deploy |
| T-05.1-07 | Tampering | `Stack.lastKnownHash` | medium | mitigate | Task 2 forbids writing an env-file hash into `lastKnownHash`. That column is the sole input to `FileWatcher`'s compose change detection; corrupting it would make external compose tampering undetectable |
| T-05.1-08 | Repudiation | status transitions triggered by manual actions | low | accept | `StackRepository.transitionStatus` already writes a `StatusLog` row per transition and that audit trail is unchanged by this plan; no per-user attribution exists yet in `StatusLog`, which is acceptable for a single-admin self-hosted deployment at ASVS L1 |

No package-manager install occurs in this plan, so no package-legitimacy gate applies.
</threat_model>
