<objective>
Make `config_error` visible in the UI (todo item M2) and make the FileWatcher notice external `.env` edits (the second half of todo item M5).

Purpose: the backend already detects a broken compose file — it logs it, writes a `config_error` `StackEvent` row, and broadcasts an SSE event — but no client code path consumes any of it, so a user editing a compose file into an unparseable state sees nothing at all. Separately, chokidar's filter only ever matches `docker-compose.yml`, so an external `.env` edit produces no event whatsoever: no hash update, no flag, nothing.
Output: a persisted `Stack.configError` with a defined lifecycle, a FileWatcher that watches and reconciles `.env` with its own hash, and error indicators on both the list and detail views.

Scope boundary: the app-driven half of M5 (`StackService.updateStack()`'s env branch calling `setConfigChanged`) is plan 05.1-02's, which lands first. This plan covers only the external-edit half.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host filesystem -> FileWatcher | files under the stacks directory are attacker-influenced input as soon as any other process can write there |
| parser error text -> `Stack.configError` -> SSE -> browser DOM | a message derived from file content is persisted and then rendered |
| `.env` file content -> hashing and event pipeline | env files hold credentials |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05.1-26 | Information Disclosure | `.env` content flowing into the watcher pipeline | high | mitigate | Task 2: only the hash of the env file is stored and only a `config_changed` event (stack id plus hash) is published. Env content, env variable names, and env values must never enter a `StackEvent` payload, an SSE event, or a log line — these files hold database passwords and API keys, and every authenticated session receives every SSE event |
| T-05.1-27 | Information Disclosure | the parser message stored in `Stack.configError` and rendered in the UI | medium | mitigate | The YAML parser's message can quote the offending line of the compose file. That is exactly the diagnostic value being added and it stays behind `requireAuth` on `GET /api/stacks`. Do not extend the stored value beyond the parser's own message — never attach file contents or the resolved host path |
| T-05.1-28 | Tampering | rendering `configError` into the DOM | medium | mitigate | Task 3 renders the message as React text content only. Never route it through `dangerouslySetInnerHTML`; a compose file is attacker-influenced input and this is a stored-XSS sink otherwise |
| T-05.1-29 | Tampering | `Stack.lastKnownHash` receiving an env-file hash | high | mitigate | Task 2 gives `.env` its own `lastEnvHash` and a separate handler, asserted by a test. Corrupting `lastKnownHash` would make external compose tampering undetectable — the watcher would compare every future compose file against an env hash and never match correctly |
| T-05.1-30 | Denial of Service | watching a second filename per stack directory | low | accept | The watcher already runs at `depth: 2` over the same tree with `awaitWriteFinish`; admitting one more filename adds a bounded, negligible amount of work. The existing `DOCKTOR_FS_POLLING` control still governs the expensive mode |
| T-05.1-31 | Repudiation | config errors and env changes | low | mitigate | Both already write `StackEvent` rows through the single `StackEventRepository.createEvent()` write path; Task 2 keeps env changes on that same path rather than introducing a second one |

No package-manager install occurs in this plan, so no package-legitimacy gate applies.
</threat_model>
