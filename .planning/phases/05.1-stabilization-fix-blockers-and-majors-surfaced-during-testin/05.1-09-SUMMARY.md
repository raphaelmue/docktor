# Phase 05.1 Plan 09: Cross-Platform Prisma CLI Resolution Summary

**One shared `resolvePrismaCliEntrypoint()` resolver replaces a hardcoded POSIX `.bin/prisma` path at both Prisma CLI call sites, launching the CLI through `process.execPath` to close a native-Windows `spawnSync ... ENOENT` defect (G-05.1-1).**

## Performance

- **Duration:** ~20 min
- **Completed:** 2026-09-03T08:08:27Z
- **Tasks:** 3
- **Files modified:** 5 (2 created source + test, 1 created todo, 2 modified)

## Accomplishments
- New `server/src/lib/prisma-cli.ts` resolves the Prisma CLI's JS entrypoint via `createRequire(import.meta.url)` and Node module resolution of `prisma/build/index.js` — no hardcoded `.bin` path, no `process.cwd()` dependence, correct in all three runtime layouts (vitest, `tsx` from source, built image).
- `server/test/integration/setup.ts`'s `startContainer()` now launches the CLI via `process.execPath` with the resolved entrypoint — verified locally: the invocation now reaches Prisma itself (a `P1001` database-reachability error matching this host's documented Docker-daemon environmental block) instead of the original `ENOENT`.
- `server/src/lib/schema-sync.ts`'s boot-time `defaultRunCli` rewired identically; `resolvePrismaBin()` (the second, independently-buggy copy of the same POSIX-path assumption) deleted outright.
- Filed `.planning/todos/pending/2026-09-03-ci-has-no-windows-runner.md` recording that CI runs only on `ubuntu-latest`, which is why this defect shipped undetected in two places simultaneously.

## Decisions Made
- Anchored resolution on `import.meta.url` module identity (via `createRequire`) rather than `process.cwd()` or relative-directory-segment counting — the single implementation is correct in vitest, `tsx`-from-source, and the built-image layouts without needing per-layout candidate paths (unlike the pre-existing `resolvePrismaConfigPath()`, which still legitimately needs candidates because it resolves a config file copied to a different relative location in the built image).
- Deleted `resolvePrismaBin()` outright instead of leaving it dead-code-adjacent — one resolution strategy, not two.
- Corrected `resolvePrismaConfigPath()`'s doc comment: its "Unlike the CLI binary, the correct relative distance differs..." framing implicitly compared itself against `resolvePrismaBin()`'s now-deleted relative-distance approach; reworded to state plainly that the config path has no platform divergence (it's a config file, not an executable) while its relative-distance concern is unchanged. No other content in that comment was touched, per the plan's "correct only whatever became false" instruction.
