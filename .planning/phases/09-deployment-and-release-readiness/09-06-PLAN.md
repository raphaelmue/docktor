<objective>
Make a user-supplied TLS certificate a real, working thing: uploaded, proven valid, stored safely, and present on disk under the name the reverse proxy actually looks for.

This is scope item 4's tracer. Task 2 wires one path — a single upload — through every layer the feature touches: HTTP multipart, server-side cryptographic validation, encryption at rest, the database, and a file in the directory nginx-proxy reads. Task 3 expands horizontally from that proven path into listing, deletion, the optional chain file, and the rejection cases.

Purpose: today the only way a Docktor-proxied domain gets a certificate is for acme-companion to issue it. That excludes internal domains with no public DNS, wildcard certificates issued elsewhere, and any certificate authority other than Let's Encrypt. The user named Nginx Proxy Manager's certificate model as the target: upload once, reuse everywhere it applies.

Output: a certificate entity that can be created, listed, and deleted over an authenticated API; validation that refuses a mismatched key, an uncovered domain, or malformed content before anything is stored; a private key that exists in plaintext only in the moment it is written to its file; and a certificate file named the way nginx-proxy resolves it.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated client → certificate upload endpoint | An authenticated but untrusted request supplies arbitrary file bytes and a domain pattern that becomes a filesystem path. |

| Docktor → nginx-proxy | A file name is the entire contract; nginx-proxy acts on whatever it finds there. |
