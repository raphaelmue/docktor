<objective>
Establish the data model for bring-your-own TLS certificates: a reusable, wildcard-capable Certificate entity, and an explicit certificate-source field on every proxy configuration.

Phase 6 shipped proxy configuration that can only obtain certificates one way — acme-companion issues them, and the only reason a domain gets one is that Docktor wrote an issuance environment variable into its compose file. There is no representation for a certificate a user already owns, and no representation for "this domain's certificate does not come from ACME." This plan adds both, as the first slice of scope item 4.

Purpose: internal domains with no public DNS, wildcard certificates issued elsewhere, and certificate authorities other than Let's Encrypt are all currently unsupported. The user named Nginx Proxy Manager's certificate model as the reference point: one upload, reusable across every subdomain it covers.

Output: shared validation schemas that know what a wildcard pattern is and what a certificate source is, a Prisma Certificate model with a restricted relation from ProxyConfig, and an ordered migration applied on top of the 0_init baseline.

**Tracer note:** this plan is the data-model foundation of scope item 4's vertical slice; plan 09-06 is the tracer proper, carrying one upload end to end from HTTP request through validation, encryption, persistence, and a file on disk. The schema is separated only because it must be generated as its own migration after 09-03's baseline lands — folding it into 09-06 would force a schema change and a behaviour change through one blocking database gate.
</objective>

<assumption_delta_decision>
**Noun promoted:** certificate source — how a `ProxyConfig` row obtains the certificate nginx-proxy serves for its domain.

Until now this was implicit and universal: every TLS-enabled proxy configuration got its certificate from acme-companion, because Docktor unconditionally wrote an issuance environment variable for it. There was no value to inspect, because there was only ever one answer.

**Decision: promote, not add-alongside.** `ProxyConfig.certSource` governs **every** row, not only rows created for custom certificates. Existing and future ACME-issued rows carry the value `acme` **explicitly** — supplied by the column's schema default, which backfills every existing row during the migration — and every code path that branches on certificate source reads the field for both values. In particular, the ACME issuance environment variable is written *because* a row's `certSource` is `acme` (wired in plan 09-07), not because the row merely lacks a custom-certificate link.

**Rationale:** modelling this as a field that only matters for custom rows would leave ACME rows silently bypassing the very field that is supposed to decide issuance, so the two paths would be governed by different mechanisms and could disagree — precisely the divergence that produces a domain with both an uploaded certificate and a live ACME challenge running against it. One field, read by both branches, cannot diverge from itself.

**Consequence, asserted in this plan:** the column is `NOT NULL` with a default, so no row can exist without an answer, and the schema-level refinement rejects the two malformed pairings (`custom` with no certificate reference, `acme` with one).
</assumption_delta_decision>

| HTTP request body → validation schema | An authenticated but untrusted request supplies a domain pattern that later becomes a filesystem path and a certificate reference that later decides whether ACME issuance runs. |
| schema definition → live database | A migration executes with schema-modification privileges against a real operator's database. |
| ProxyConfig row → acme-companion | The presence or absence of an issuance environment variable, derived from the certificate-source field, is what makes an external container act on a domain. |
