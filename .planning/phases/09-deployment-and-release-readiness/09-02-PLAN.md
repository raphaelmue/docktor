<objective>
Give this project a CI signal on the two platforms its contributors actually develop on but its pipeline has never exercised.

Today `.github/workflows/ci.yml` has exactly one test job, on `ubuntu-latest`. STATE.md already records one Windows-only defect that shipped and had to be fixed after the fact (`path.resolve` vs `path.join` drive-letter duplication in the backup path handling, Phase 04), and another (Prisma CLI resolution via Node's own binary, plan 05.1-09). Neither was catchable by this pipeline.

Purpose: a self-hosting product whose contributors run Windows and macOS cannot keep discovering platform-divergent defects through user reports. D-07 makes these checks blocking from day one precisely so the signal cannot be ignored.

Output: one matrix job covering `windows-latest` and `macos-latest` with typecheck plus all three unit suites and nothing Docker-dependent, a human-performed branch-protection change making both required, and scope item 3's todo closed.

**Tracer note:** TRACER_MODE is active for this phase, but a single CI job definition is not decomposable into a vertical slice plus horizontal expansion — the job either exists in the workflow file and runs, or it does not. Task 1 is therefore authored as one complete, production-quality change rather than a tracer followed by expansion tasks. The end-to-end proof is a real workflow run, which Task 2 gates on.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| pull request → CI runner | Untrusted contributor code executes on GitHub-hosted runners with the workflow's secrets and permissions in scope. |
| CI result → merge gate | A green check is the signal a human uses to decide a change is safe to merge. A check that cannot fail is worse than no check. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-05 | Spoofing | `cross-platform-unit` check result | high | mitigate | A required check that runs zero server tests spoofs safety: it reports "server code verified on Windows" while having verified nothing. Mitigated by the mandatory explicit `yarn workspace @docktor/server test:unit` step, an acceptance criterion asserting that literal command is present in the job, and a human-check that inspects the step's observed duration for the zero-tests signature. |
| T-09-06 | Elevation of Privilege | new job's permissions and secrets | medium | mitigate | The job declares only the two non-secret env values the ubuntu job already uses (`BETTER_AUTH_SECRET: ci-test-secret`, `NODE_ENV: test`), inherits no additional `permissions:` block, and is explicitly forbidden from containing any SonarQube step — so `SONAR_TOKEN` is never exposed to a runner executing on a pull-request matrix. |
| T-09-07 | Tampering | supply chain of CI actions | medium | mitigate | Only actions already trusted and pinned by the existing ubuntu job are reused (`actions/checkout@v4`, `actions/setup-node@v4`). No new third-party action is introduced. Dependency installation uses `yarn install --immutable`, so a lockfile-divergent dependency tree fails the job rather than silently installing. |
| T-09-08 | Denial of Service | `fail-fast: false` doubling runner minutes | low | accept | Accepted per D-08: keeping both platforms running when one fails is worth the extra minutes during stabilization, and is the only way a Windows failure does not mask a macOS failure. |

No package-manager install of a new dependency occurs in this plan (`yarn install --immutable` installs only the existing, lockfile-pinned tree), so `T-09-SC` does not apply here; it is registered in plan 09-06.
</threat_model>
