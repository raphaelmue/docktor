2. **WR-07 TOCTOU** — the `Setting.key` unique-primary-key lock in `routes/setup.ts:65-71` cannot be proven by static analysis or by the existing non-concurrent suite. Race two `step1` requests against a real Postgres container and assert exactly one admin is created.

This plan supplies those executed tests so the phase can be closed without a manual sign-off.

<rationale>
**Why these are in scope for a gap-closure run.** Neither item is the blocking gap — that is WIZ-01, handled by plan 05-09. Both were flagged by the verifier as needing human or integration verification rather than a fix. They are planned here rather than deferred because none of the three legitimate deferral reasons applies: the information needed is present (`MigrationService` takes all five collaborators through constructor parameters, and `server/test/integration/setup.ts` already stands up a real Postgres via testcontainers with `app.inject`), the context cost is modest, and there is no dependency on unshipped work. `CLAUDE.md` additionally makes this mandatory rather than optional: "Every new feature and bug fix must have corresponding tests. Tests must cover both the happy path and edge cases / error paths."

**Why a unit test and not an integration test for BF-05.** The rollback invariant is a filesystem-and-orchestration invariant, not a database one. `MigrationService` injects `DockerExecutor`, `VolumeMigrator`, `ComposeRewriter`, `StackFilesystem` and `StackRepository` as constructor parameters with singleton defaults, so the failure can be injected precisely (`docker.up` rejects) while the filesystem work runs for real against `os.tmpdir()` fixtures. That gives a genuine byte-for-byte restore assertion without needing Docker or Postgres.

**Why the concurrency test uses `app.inject`.** `server/test/integration/setup.ts` already builds the real Fastify app against a real `postgres:17` container. Firing both injections inside a single `Promise.all` interleaves them at their `await` points, which is exactly where the count-then-create window lives. If the two happen to serialize, the losing request still returns 400 through the durable `userCount > 0` guard — so the assertion is deterministic either way while still exercising the race when it occurs.

**Deliberate non-goal.** `VolumeMigrator` remains untested. Its two methods shell out to `docker run`, so covering them needs a live daemon and a real named volume; that is a separate integration concern and is not required by any Roadmap truth. Recorded here rather than silently dropped.
</rationale>
