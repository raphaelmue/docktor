<objective>
Close the one blocking gap in 05-VERIFICATION.md: the server's first-run gate is correct, but no client code consumes it, so a fresh install renders the login form instead of the setup wizard (Roadmap SC-1 / WIZ-01).

Wire a client-side first-run gate: a `useSetupStatus` hook that owns the `GET /api/setup/status` server state, and a `FirstRunGate` component that diverts session-less visitors to `/setup` when the instance has no users — while failing safe to the existing `/login` behavior on any status-check error.

Purpose: make the phase's headline success criterion literally true — on first boot the browser shows the wizard, not the login page.

Output: `/` and `/login` both land a first-boot visitor on the setup wizard; the previously-skipped WIZ-01 Playwright test runs green; the existing auth E2E suite is made deterministic against the new status call.
</objective>

<rationale>
**Why client-side and not a server-side 302.** `05-CONTEXT.md` and `05-RESEARCH.md` both describe the entry mechanism as "server middleware redirects to /setup". What shipped in `server/src/app.ts:63-87` is an API-level 503 `{error, redirectTo}` gate that deliberately exempts every non-`/api/` URL (`!request.url.startsWith("/api/")` returns early). Converting that into a document-level `reply.redirect(302, "/setup")` was considered and rejected for three concrete reasons: (1) Fastify only serves the SPA when `env === "production"` (`app.ts:147-161`) — in development and under Playwright the client is served by Vite on `:5173`, so a server-side document redirect would do nothing in the exact environment the WIZ-01 acceptance test runs in; (2) the `onRequest` hook was just narrowed by the WR-08 fix, and re-widening it to match document navigations reopens the asset/route-scoping regression that fix closed; (3) `05-VERIFICATION.md` names the client-side check as the missing piece. The decision's *intent* — a first-boot visitor lands on the wizard — is honored; the server gate stays as defense in depth.

**Why a hook plus a gate component, not an inline `useEffect`.** `05-PATTERNS.md` sketches the fix as a `useEffect` + `checkSetupStatus()` inline in `ProtectedRoute`. Project canon in `CLAUDE.md` forbids that ("Do not fetch data directly in React components — use a custom hook"; "Custom hooks are the single source of truth for server state"). The state machine therefore lives in `useSetupStatus`, and the render decision lives in `FirstRunGate`, which is a real file and is therefore unit-testable — `main.tsx` cannot be imported by a Vitest test because it calls `createRoot(...).render(...)` at module scope.

**Why `ProtectedRoute` is not extracted to its own file.** Once `FirstRunGate` carries the whole decision, `ProtectedRoute` retains four lines of session branching. Extracting it would add a file and an import edge for no testable behavior; all branch logic is covered by the `FirstRunGate` unit tests plus the WIZ-01 E2E test. Left inline deliberately, not overlooked.

**Deliberate non-goal: `/signup`.** On a zero-user instance `/signup` still works and creates a user through better-auth, bypassing the wizard. That is a pre-existing hole in the phase-3/phase-5 auth surface, is outside both WIZ-01's text ("instead of the login page") and this gap's `missing` list, and is recorded here rather than silently dropped.

**Flagged assumption (edge-probe fallback).** No `SPEC.md` exists for phase 05, so the deterministic edge probe returned WIZ-01 as `unclassified`/`unresolved`. The edges were classified by hand and authored into `must_haves.truths` above: status-fetch failure fails safe to `/login`; `setupComplete: true` with no session still goes to `/login`; in-flight status renders a loading shell rather than flashing the login form. The two-tabs-race-on-first-boot edge is explicitly *not* this plan's concern — that is the WR-07 TOCTOU lock, covered by plan 05-10.
</rationale>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-09-01 | Tampering | `FirstRunGate` navigation target | medium | mitigate | The destination is the hardcoded literal `/setup` inside `first-run-gate.tsx`. The server's 503 body carries a `redirectTo` field, but no client code reads it — a spoofed or compromised API response cannot steer a visitor to an attacker-chosen URL. Enforced by an acceptance-criteria grep asserting `redirectTo` never appears in the gate component. |
| T-05-09-02 | Elevation of Privilege | `/setup` account-creation wizard exposure on a configured instance | high | mitigate | Two independent layers. Client: the `"error"` status branch renders the caller's `/login` fallback, never `<Navigate to="/setup">`, so a transient outage or an injected 5xx cannot surface step 1. Server: `routes/setup.ts:24-32` already returns 410 for every setup route other than status/step1 once `userCount > 0`, and step 1 itself returns 400 (`:50-53`) — so even a client tricked into rendering the wizard cannot create a second admin. Covered by a dedicated failing-status unit test in Task 2. |
| T-05-09-03 | Information Disclosure | unauthenticated `GET /api/setup/status` | low | accept | Discloses a single boolean, "is this instance configured". Pre-existing endpoint (shipped in 05-03), already inferable from the 503 gate's behavior on any other `/api/*` route. This plan adds callers, not exposure. |
| T-05-09-04 | Denial of Service | extra status request per unauthenticated render | low | accept | One additional `SELECT count(*)` per session-less page load, only on the unauthenticated path; the hook short-circuits entirely when a session exists. |
| T-05-09-SC | Tampering | npm/yarn installs | n/a | accept | This plan adds zero dependencies — no `package.json` or `yarn.lock` change. The Package Legitimacy Gate is not applicable and no `[ASSUMED]`/`[SUS]` checkpoint is required. |
