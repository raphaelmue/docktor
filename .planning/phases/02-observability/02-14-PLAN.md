<objective>
Stop the stack detail page from remounting itself every time an SSE event arrives.

Purpose: UAT test 12 passed functionally but the user reported it "looks like the page was refreshed". The debug session found why: `useStack` drives one `loading` boolean for both the first load and every SSE-triggered refetch, and the page early-returns a small placeholder tree whenever that flag is true. Because the placeholder is structurally unrelated to the real page, React tears down the whole tree — tabs, scroll areas, everything — and rebuilds it milliseconds later on every `config_changed` and `update_available` event.

Output: A hook that distinguishes a first load from a background refresh, a page that only shows the placeholder when it has no data at all, and tests that pin the distinction.
</objective>

    - Once the first fetch resolves, loading is false and the stack is populated — unchanged from today

  <action>
Rewrite the fetching in `client/src/hooks/use-stack.ts` around one internal function that takes an explicit mode rather than one that guesses.

Define the fetch as accepting a mode of either initial or background. In initial mode it behaves exactly as the current code does: it sets the loading flag, clears the error, and on failure records the error message and leaves the stack null. In background mode it sets an `isRefreshing` flag instead, never touches the loading flag, and on failure leaves both the stack and the error untouched, logging a warning to the console so the failure is not invisible to a developer. That asymmetry is the fix: the error state is as destructive as the loading state here, because the page's error branch replaces the same tree.

The mount effect calls the initial mode. Both SSE handlers — `config_changed`, which keeps its existing toast, and `update_available` — call the background mode. Expose `refetch` as a stable zero-argument callback that runs a background refresh, because every caller of it already holds rendered data: `StackActions` passes it as `onAction` and `ServicesTab` passes it as `onUpgraded`, both invoking it with no arguments. Keep the returned object shape otherwise as it is and add `isRefreshing` to it.

Leave the `container_state` and `stack_status` branches exactly as they are. They already merge into state without touching any flag, which is why those events never produced the reported symptom.

Then fix the page. In `client/src/routes/app/stacks/[id].tsx`, gate the placeholder early return on there being no stack yet as well as the load being in progress, so the placeholder is reachable only before the first successful load. Leave the error early return as it is; the hook change already keeps a background failure from reaching it.

Surface the refresh instead of hiding it. Render a small muted indicator inside the existing `PageActions`, next to the status badge, only while `isRefreshing` is true — a short piece of text or an existing icon, with no layout shift when it appears. The point of this plan is that a background refresh stops destroying the page, not that it becomes invisible.

Update `client/test/unit/hooks/use-stack.test.ts` to drive events. Add a module mock for `@/hooks/use-container-events` whose implementation captures the handler passed to it into a test-scoped variable, so a test can invoke it directly; add a module mock for `sonner` so the toast in the `config_changed` branch does not reach the real toaster. Keep the existing `@/lib/stacks-api` mock and the four existing tests, which must still pass. Add tests for every case in the behavior list, driving each event through the captured handler wrapped in `act` and asserting with `waitFor` in the style already used in that file.
  </action>
