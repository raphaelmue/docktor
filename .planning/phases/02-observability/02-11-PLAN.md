<objective>
Make an image update a real version upgrade that persists in the compose file, instead of a pull-and-deploy whose effect disappears on the next restart.

Purpose: UAT Gap 5 (major, test 12). The user's report was precise: the feature works, but "the 'update images' is rather a pull and deploy", and what is wanted is to pick a version and have "the docker-compose adjusted automatically". Two of the three sub-asks are already done — the "already up to date" toast was delivered by plan 02-07 and is live at `stack-actions.tsx:82-96`. What remains is persisting a chosen version, which is this plan, and offering the choice, which is plan 02-12. This plan builds the whole server side so the client work stays thin.

Output: A format-preserving compose editor, an application-service upgrade operation with rollback, and an authenticated per-service upgrade endpoint.
</objective>

Create `server/src/lib/compose-editor.ts`. Implement `setServiceImageTag(content, serviceName, newTag)` using the `yaml` package's document API — `parseDocument`, then a targeted `setIn` on the path through `services`, the service name, and `image`, then `toString()`. The document API is required rather than `parse` plus `stringify` because the latter discards comments and normalizes formatting, which would rewrite the operator's whole file on every upgrade. Read the existing image string first, split off any existing tag using the last-colon-that-is-not-a-port rule (the same rule `splitImageRef` uses in `update-checker.ts` — reuse that helper if importing it here does not violate layering; if it does, restate the rule locally and note why), then write back the name joined to `newTag`. Raise `ComposeEditError` when `services` is absent, when the named service is absent, when the service has no `image` key, or when the current image is pinned by digest with an `@sha256:` suffix — a digest pin has no tag to swap and must not be guessed at.

Add `upgradeServiceSchema` and `upgradeServiceParamsSchema` to `shared/src/validation/stacks.ts` and re-export them from `shared/src/validation/index.ts`. The params schema extends the stack params with a `serviceName` string. The body schema carries a single `targetTag` constrained by a strict Docker tag pattern: a leading word character or digit followed by up to 127 characters drawn from letters, digits, underscore, period and hyphen. This regex is the security control that keeps an attacker-supplied string from being interpolated into a YAML document, so it is not optional and it belongs in the shared package, not inline in the route.

Add `upgradeServiceImage(id, serviceName, targetTag)` to `StackService` in `server/src/application/stack-service.ts`, returning `{changed, previousTag, newTag}`. Model the body on `updateImages()`. Determine the current tag for that service; if it already equals `targetTag`, return `{changed: false}` immediately with no write and no transition — this is the idempotency guarantee. Otherwise call `guardTransition(stack.status, "UPDATE")` so the same status rules that protect `updateImages` apply, transition to UPDATING, compute the new content with `setServiceImageTag`, write it with `this.fs.writeCompose(id, newContent)`, then `composePull` and `up`. Translate a `ComposeEditError` into a `BadRequestError` and a missing service into a `NotFoundError`, per the CLAUDE.md rule that business code throws from the typed hierarchy.

Return the service result plus `success: true`, matching the shape of the existing update route.

    - Given `composePull` rejects after the compose file was rewritten, when `upgradeServiceImage` runs, then the original compose content is written back to disk, the stack transitions to ERROR, and the error propagates to the caller.
    - Given `up` rejects after a successful pull, when `upgradeServiceImage` runs, then the original compose content is restored and the stack transitions to ERROR.
    - Given the restore write itself fails, when `upgradeServiceImage` runs, then an error is logged naming the stack and the original deploy error is still the one propagated.
    - Given the deploy succeeds, when `upgradeServiceImage` runs, then no restore occurs and the new content remains on disk.

  <action>
Capture the compose content read at the start of `upgradeServiceImage` in a local constant before any write, and wrap the pull-and-recreate section in a try/catch. In the catch, restore the captured original with `this.fs.writeCompose(id, originalContent)` before transitioning the stack to ERROR and rethrowing. Without this, a failed upgrade leaves a compose file on disk that names a version the stack is not running and was never able to run — the operator's file has been silently changed by a failed operation, which is worse than the pull-and-deploy behavior being replaced.

Guard the restore itself in a nested try/catch. If restoring fails, log it with the established prefix convention naming the stack id, then continue to the ERROR transition and rethrow the original deploy error, not the restore error — the deploy failure is the actionable cause and must not be masked.

Order the catch so the ERROR transition happens after the restore attempt, so a subsequent reconcile observes the restored file rather than the failed one.

Note the interaction with FileWatcher and state it in the summary: the write, and the restore if it happens, both change the file hash, so a `config_changed` event may fire for the intermediate state. The success path already calls `clearConfigChanged(id)`; on the failure path the flag is allowed to remain set, which is correct, because the operator should see that the file was touched.

Add cases to `server/test/unit/application/stack-service.test.ts` for each behavior bullet, asserting on the order and arguments of `writeCompose` calls with `mock.invocationCallOrder` — specifically that the final `writeCompose` on a failure path carries the original content. Assert that the error surfaced from the failing-restore case is the deploy error.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> upgrade endpoint | An authenticated user supplies a stack id, a service name and a target tag that will be written into a file on the host |
| application service -> host filesystem | The only write path in this plan targets operator-owned compose files |
| compose file -> Docker daemon | The rewritten file is executed by `docker compose up` |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-11-01 | Tampering | `targetTag` written into docker-compose.yml | high | mitigate | `upgradeServiceSchema` constrains the tag to the Docker tag grammar in the shared package, rejecting whitespace, newlines, quotes and YAML metacharacters before the value reaches the editor; the value is set through the YAML document API as a scalar node rather than by string concatenation into the raw text |
| T-02-11-02 | Elevation of Privilege | Upgrade endpoint reachable without user intent | high | mitigate | The route sits behind `requireAuth`, the service is resolved from the addressed stack's own list, and no job, cron or background path imports `upgradeServiceImage` — verified by grep in the acceptance criteria. This preserves the UPD-04 never-automatic guarantee |
| T-02-11-03 | Tampering | Write path escaping the stack directory | high | mitigate | The write goes exclusively through `StackFilesystem.writeCompose(id, ...)`, which resolves under the stack root from the stack id; `serviceName` selects a YAML key and never contributes to a path |
| T-02-11-04 | Denial of Service | Failed upgrade leaving an unusable compose file | high | mitigate | Task 3 restores the captured original content on any pull or recreate failure, so a failed operation cannot strand the stack on a file it cannot deploy |
| T-02-11-05 | Repudiation | Version change with no trace | medium | mitigate | The upgrade returns `previousTag` and `newTag` and moves the stack through the recorded UPDATING to RUNNING transitions, so the change appears in the existing status history |
| T-02-11-06 | Tampering | npm/yarn installs | high | mitigate | No new dependencies — `yaml` is already a server dependency. `yarn.lock` must be unchanged; if an install seems necessary, stop and request a package legitimacy audit |
</threat_model>
