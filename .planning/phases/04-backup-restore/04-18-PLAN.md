<objective>
Close verification gap **WR-01** (04-VERIFICATION.md, `gaps_remaining`) against ROADMAP Success Criterion #2 / requirement **BCK-03**: "User can trigger a manual backup for any stack and see streaming progress output in the UI".

Today, a transient disconnect while a backup is running blanks the user's visible log the moment the automatic reconnect succeeds. Two halves cause it:

1. `client/src/hooks/use-backup-stream.ts` `connect()` calls `setLines([])` on every invocation, including the reconnect that `scheduleReconnect()`'s timer fires.
2. `server/src/routes/backups.ts` `/stream` live-emitter branch only forwards *future* `emitter.on("line", ...)` events. It never replays lines already emitted for a still-`IN_PROGRESS` backup, so the cleared pane is never refilled.

**Chosen fix direction: (2) server-side replay** — the second option in 04-VERIFICATION.md's `missing:` list. Rationale, recorded so the next reviewer does not re-litigate it:

- It makes the server the single authority for log content on **every** subscription. The two terminal branches already replay `backup.logLines`; adding replay to the live branch completes the invariant. Once the invariant holds, the client's existing `setLines([])` becomes *correct* rather than defective — it is exactly what prevents duplication.
- The alternative (option 1: gate the client clear to first-connect-only) introduces a **new** defect. If the backup finishes during the disconnect window, the reconnect lands on the already-terminal branch, which replays the full stored `logLines`. Preserved lines + replayed lines = a visibly duplicated log. Option 1 would trade WR-01 for a duplication bug.
- Option 2 also heals the hole option 1 cannot: lines emitted *while the client was disconnected* are delivered on reconnect. Option 1 leaves a silent gap in the log.
- Memory cost is zero-delta. `runBackup` (line 182) and `runRestore` (line 285) already allocate `const lines: string[] = []`, already accumulate every line into it, and already persist it as `logLines`. This plan makes that existing array reachable by the route instead of allocating a second one. Peak memory and lifetime are unchanged; the buffer is freed by the `disposeBackupBroadcaster` call that already runs in both `finally` blocks.

Per CLAUDE.md ("Route handlers must be thin — extract logic into services immediately if more than ~10 lines"), the ~20-line live-branch subscribe block moves into a new HTTP-agnostic helper `server/src/lib/sse-backup-log.ts`, which makes the replay-then-subscribe ordering deterministically unit-testable without standing up a Fastify socket. 04-VERIFICATION.md's WR-02 records that this endpoint has *zero* route-level coverage; this plan does not fix WR-02 in general, but it does ensure the line it changes is covered.

Purpose: make "see streaming progress output in the UI" survive a transient disconnect, which is the exact path the last three gap-closure rounds (04-15, 04-16, 04-17) were built to harden.

`streamLiveBackupLog` returns `new Promise<void>((resolve) => { ... })` whose executor body runs, **in this exact order and with no `await` anywhere between them**:
  1. Take a snapshot: `const replay = [...args.buffered]`.
  2. For each line in `replay`, call `args.port.write(formatLogLineFrame(line))`.
  3. Define `onLine(line: string)` calling `args.port.write(formatLogLineFrame(line))`.
  4. Define `onDone(finalStatus?: string)` which writes `formatDoneFrame(finalStatus ?? args.fallbackStatus)`, detaches both listeners, calls `args.port.end()`, then `resolve()`.
  5. Attach `args.emitter.on("line", onLine)` and `args.emitter.once("done", onDone)`.
  6. Call `args.port.onClientClose(...)` with a handler that detaches both listeners via `off` and calls `resolve()` — and does **not** call `end()`, because the client socket is already gone.
