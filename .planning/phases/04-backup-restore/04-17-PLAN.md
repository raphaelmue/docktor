<objective>
Close the three confirmed defects that keep ROADMAP Success Criterion #2 ("User can trigger a manual backup for any stack and see streaming progress output in the UI") at partial: the backup detail page can still tell the user the wrong thing, or nothing at all, while a backup is genuinely still running.

Purpose: plans 04-15 and 04-16 closed the case where the stream reaches a real terminal status. They did not close the three cases where it does not. CR-01 — `es.onerror` sets `disconnected` and closes the EventSource with no retry, and the page's one-shot resync cannot re-fire because a refetch that still returns `IN_PROGRESS` changes none of its dependencies, so a dropped connection freezes the page until a manual reload. CR-02 — the SSE route treats a missing broadcaster as "already finished" and ends the stream with the current DB status, but the broadcaster is only registered inside `runBackup`, which runs after the fire-and-forget `Promise.all`; a client that opens `/stream` in that window is handed `{done: true, status: "IN_PROGRESS"}`, which the hook reads as a failed backup. CR-03 — `initiateBackup` writes `resticSnapshotId: ""` on every new row, and the page's `shortId` falls back with nullish coalescing, which does not catch an empty string, so the title and breadcrumb render blank on the single most common state this page is viewed in.

Output: broadcaster registration moved to backup-creation time behind a single register/dispose pair, a re-reading SSE fallback branch, a bounded EventSource reconnect, a bounded self-terminating record poll for the disconnected case, and an empty-string-safe short id — each with unit coverage.

No `type="tracer"` slice is used: this is a three-defect repair across an already-proven end-to-end path, and the vertical slice it would trace is exactly the path 04-15/04-16 already built and tested.
</objective>

In `server/src/application/backup-service.ts`, add two exported functions next to the existing `getBackupBroadcaster`, and make them the sole gatekeepers of the module-level `backupBroadcasters` map:

`ensureBackupBroadcaster(backupId: string): EventEmitter` returns the map entry for `backupId` when one exists, and otherwise constructs an `EventEmitter`, stores it under `backupId`, and returns it. This is the only place in the file permitted to write to the map.

`disposeBackupBroadcaster(backupId: string): void` looks the entry up, calls `removeAllListeners()` on it when present, and deletes the key. This is the only place in the file permitted to remove from the map.

Then rewire the four call sites:

1. `initiateBackup` — immediately after the `this.backupRepo.create({...})` call resolves, call `ensureBackupBroadcaster(backup.id)` and discard the return value. This runs before the `stackRepo.update` call and before the method returns, which is what closes the race: the route cannot send `202 {backupId}` until `initiateBackup` has resolved, so any client that learns the id finds a live emitter.
2. `runBackup` — replace the inline emitter construction and the map write at the top of the method with `const emitter = ensureBackupBroadcaster(backupRecord.id)`, and replace the map deletion in the `finally` block with `disposeBackupBroadcaster(backupRecord.id)`. Everything else in the method, including `emitter.emit("done", finalStatus)`, stays exactly as it is.
3. `runRestore` — the same two substitutions against `backup.id`, keeping the method symmetric with `runBackup` as `04-PATTERNS.md` requires.
4. `abortBackup` — keep the existing early-return guard on `!backup || backup.status !== "IN_PROGRESS"` exactly as it is and return before touching the emitter, because on that path `runBackup` still owns it. Past the guard, wrap the existing body (the `backupRepo.update` to FAILED, the `stackRepo.update` to ERROR, the displayName lookup and the `notificationService.notify` call) in a `try` whose `finally` calls `getBackupBroadcaster(backupId)?.emit("done", "FAILED")` and then `disposeBackupBroadcaster(backupId)`. Using `finally` is deliberate: a rejected `notify()` must not be able to strand a subscribed SSE client with a stream that never ends.

In `server/src/routes/backups.ts`, rewrite the missing-broadcaster branch of `GET /api/backups/:id/stream` (currently a single unconditional `{done: true, status: backup.status}` write).
