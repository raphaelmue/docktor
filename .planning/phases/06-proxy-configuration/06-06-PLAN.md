<objective>
Offer the managed proxy stack at the moment a new install is being configured, as an
optional wizard step, exactly as D-10 specifies — not lazily on the first domain
assignment, and not as a required field the user must fill to reach the dashboard.

Purpose: PRXY-03's "configurable in Settings" is already met by 06-03/06-05; this plan
adds the second, discoverability half that D-09 and D-10 call for, so a fresh install
does not have to know the Proxy tab exists before it can use it.

Output: `wizardStep6Schema`, `OnboardingService.handleWizardStep6`, a
`POST /api/setup/step6` route, a `ProxyStep` component, and the wizard renumbering that
makes Proxy the terminal step.
</objective>

<planner_decisions>
- **Step placement — RESOLVED: appended as step 6, after Import.** Inserting Proxy at
  position 5 would renumber the existing Import step and every literal `5` in
  `setup.tsx`'s `handleSkip`/`handleFinish` terminal branches plus the brownfield
  wiring. Appending is the smaller, better-contained change, and the ordering reads
  correctly: adopt your existing stacks first, then expose them.
- **Wizard endpoint auth — RESOLVED: a new `POST /api/setup/step6` under the existing
  setup plugin, not a call to the authenticated Settings endpoints.** Whether the
  wizard client holds a session immediately after step 1 is not established anywhere in
  the codebase (`routes/setup.ts` line 85 carries a comment claiming step 2 "requires
  auth after step 1", but no `requireAuth` hook exists on that plugin), so routing the
  wizard through `requireAuth`-gated endpoints could 401 a fresh install. The step6
  route therefore inherits the same gating steps 2 through 5 already have, **plus** an
  explicit `userCount === 0` rejection mirroring `/api/setup/complete`, which narrows
  its reachable window to "after an admin exists, before the wizard is finished". The
  residual exposure is recorded in the threat register as inherited, not introduced.
</planner_decisions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| unauthenticated browser -> `POST /api/setup/step6` | reachable during the wizard window like every other setup step |
| wizard-supplied `acmeEmail` -> `proxy.acmeEmail` setting -> generated compose file | untrusted string reaches a file the Docker daemon executes against |
| `POST /api/setup/step6` -> host ports 80/443 | an unauthenticated caller in the wizard window can cause containers to bind privileged host ports |

## STRIDE Threat Register (ASVS L1, blocking on `high`)

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-30 | Spoofing | `POST /api/setup/step6` reachable without a session | high | mitigate | narrowed on both sides: the plugin's existing `isWizardComplete()` preHandler 410s it once the wizard finishes, and a new `userCount === 0` rejection 400s it before an admin exists — leaving only the same window steps 2 through 5 already occupy. This is an inherited property of the wizard plugin's design (`routes/setup.ts` lines 20-36), not a surface Phase 6 introduces; a blanket `requireAuth` on the whole plugin is a change to Phase 5's contract and belongs in its own phase |
| T-06-31 | Tampering | wizard `acmeEmail` reaching the generated compose file | high | mitigate | identical control chain to the Settings path: `wizardStep6Schema` enforces the email shape at the Fastify boundary, `updateProxySettings` re-validates, and `renderProxyStackCompose` emits the value as a `JSON.stringify` double-quoted YAML scalar (T-06-14) |
| T-06-32 | Denial of Service | an unauthenticated wizard-window caller binding host ports 80/443 | medium | mitigate | `deployProxyStack`'s `assertHostPortsFree` pre-flight refuses when the ports are taken, so the worst case is deploying the intended proxy stack rather than displacing an existing service; the window is bounded by T-06-30's two gates |
| T-06-33 | Repudiation | a deploy failure leaving `proxy.acmeEmail` persisted | low | accept | deliberate ordering: persisting first means the user can retry the deploy from Settings without retyping. The Stack row is only created after the port pre-flight passes, so a failed deploy leaves no half-registered stack |
</threat_model>
