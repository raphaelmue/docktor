<objective>
Expand the proven tracer slice from "one domain, one direction" to the full
configuration lifecycle: remove a domain, re-apply an existing one idempotently,
carry several domains on one service without losing any, and serialize the
read-modify-write cycle so two in-flight requests cannot clobber each other's edits.

open. This is also where the D-08 promote invariant earns its keep — every path here
renders the whole domain set for a service, never a single row.

idempotent `assignDomain` in `ProxyService`, adoption of hand-written domains, a
`keyed-mutex` primitive, the live `DELETE /api/proxy-configs/:id` handler, and unit +
integration coverage including a held-out concurrency test.
</objective>

  <behavior>
    `removeServiceProxyEnv(content, serviceName)` (compose editor):
    - Deletes `services.{name}.environment.VIRTUAL_HOST`, `.VIRTUAL_PORT` and `.LETSENCRYPT_HOST` when present, and is a no-op for any of them that is already absent.
    - Removes the `docktor_proxy` entry from `services.{name}.networks`, leaving any other network entries in their original order.
    - When `services.{name}.networks` becomes empty, deletes the `networks` key from that service rather than leaving an empty list.
    - Leaves the top-level `networks.docktor_proxy` declaration in place — another service in the same file may still need it.
    - Leaves every other service, comment and quoting style byte-identical.
    - Unknown service name throws `ComposeProxyEditError` with `reason === "service-not-found"`.

    `ProxyService.removeDomain(proxyConfigId)`:
    - Unknown id throws `NotFoundError` (HTTP 404) — this is the "clear not-found response" half of the PRXY-04 idempotency truth.
    - With other rows still present for the service: deletes the row, re-renders the remaining domain set through `setServiceProxyEnv`, writes the file, redeploys.
    - With no rows left for the service: deletes the row, calls `removeServiceProxyEnv`, writes the file, redeploys.
    - A second call with the same id returns 404 and performs no compose write.
    - Removing service A's last domain does not touch service B's `VIRTUAL_HOST` or B's `docktor_proxy` network entry in the same file.

    `ProxyService.assignDomain` adoption path:
    - When the target service's compose file already lists domains in `VIRTUAL_HOST` that have no `ProxyConfig` row for that `(stackId, serviceName)`, those domains are created as rows (inheriting the file's `VIRTUAL_PORT` as `internalPort` and `tlsEnabled: true` when they also appear in `LETSENCRYPT_HOST`, otherwise `false`) before the new domain is added, and all of them survive into the rewritten `VIRTUAL_HOST`.
    - An adopted domain that collides with a row owned by another service is skipped with a warning rather than aborting the assign, because the file is the pre-existing state the user already had.
  </behavior>

  <behavior>
    `withKeyedLock(key, fn)` (`server/src/lib/keyed-mutex.ts`):
    - Runs `fn` and resolves with its result.
    - Two calls with the SAME key never overlap: the second `fn` starts only after the first settles. A test proves this by having the first `fn` record a start/end marker around an `await` of a deferred promise and asserting the second `fn`'s start marker lands after the first's end marker.
    - Two calls with DIFFERENT keys may overlap.
    - A rejecting `fn` propagates its rejection to its own caller and still releases the lock, so a later call with the same key runs.
    - The internal map does not grow without bound: the entry for a key is dropped once its chain is idle.

    `ProxyService.assignDomain` idempotency (PRXY-05):
    - A domain already owned by the SAME `(stackId, serviceName)` updates that row's `internalPort` and `tlsEnabled` through `proxyRepo.updateConfig` and re-syncs the compose file; the row count for that pair is unchanged and no `ConflictError` is raised.
    - A domain owned by a DIFFERENT service still raises `ConflictError`.
    - Re-assigning identical values twice leaves the compose file byte-identical after the second call.

    Concurrency (the held-out backstop test):
    - Five `assignDomain` calls for the same stack and service with five distinct domains, all started before any resolves, end with a compose file whose `VIRTUAL_HOST` contains all five domains, and with five `ProxyConfig` rows. No domain is lost to a read-modify-write race.
    - An `assignDomain` and a `removeDomain` for the same stack started concurrently end with a compose file consistent with the final database rows (the file's domain set equals the row set).
  </behavior>

  <action>
Create `server/src/lib/keyed-mutex.ts` exporting an async function `withKeyedLock`,
generic over its return type T, taking `key: string` and a zero-argument callback
returning a promise of T, and itself returning a promise of T.
Back it with a module-level `Map` from key to the tail of that key's promise chain.
Each call appends `fn` to the tail, awaits its own link, and — in a `finally` — deletes
the map entry when the stored tail is still the one this call appended (that identity
check is what keeps the map from growing without bound while remaining correct when a
later call has already appended). A rejection inside `fn` must not poison the chain for
subsequent callers: swallow it on the chain that later callers await, and rethrow it
only to the caller that owns it. Keep this file dependency-free so it stays trivially
unit-testable — no imports beyond what TypeScript needs.

In `server/src/application/proxy-service.ts`:

- Import `withKeyedLock` and wrap the whole body of `assignDomain` and of `removeDomain`
  in `withKeyedLock(stackId, async () => { ... })`. Key on the **stack id**, not the
  service name: a stack has one `docker-compose.yml`, so two services in the same stack
  are still the same read-modify-write target. `removeDomain` must look up the row to
  learn its `stackId` before it can take the lock, so do the `findByIdOrThrow` outside
  the lock and re-read the row inside it.
- Add the idempotent branch at the top of `assignDomain`'s locked body: query
  `proxyRepo.findByStackAndService(stackId, serviceName)` for a row whose `domain`
  equals the incoming domain. When found, call
  `proxyRepo.updateConfig(row.id, {internalPort, tlsEnabled})` and skip the create
  entirely, then continue to the shared `syncServiceComposeProxy` call. Only a domain
  that is absent from this service's rows goes through `create`, so the `P2002`
  translation added in Task 1 now fires only for a genuine cross-service collision.
- Relax the port-consistency guard accordingly: an idempotent re-assign of an existing
  domain is allowed to change the port for the whole service (all rows for the pair are
  updated to the new `internalPort` in that case), because nginx-proxy permits only one
  `VIRTUAL_PORT` per container and the user's explicit re-assign is the instruction to
  change it. A *new* domain with a conflicting port still raises `BadRequestError`.

Write the `keyed-mutex` unit tests and the concurrency tests in
`proxy-service.test.ts` first. The concurrency test uses in-memory fakes for the
repository and a fake filesystem whose `readCompose`/`writeCompose` operate on a single
string held in the closure with an artificial `await new Promise(setImmediate)` between
read and write — without that interleaving window the test would pass even with the
lock removed, and would prove nothing. Assert the test fails with the lock removed
before accepting it as green.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> `DELETE /api/proxy-configs/:id` | an untrusted opaque id crosses here |
| two concurrent HTTP requests -> one stack's `docker-compose.yml` | interleaved read-modify-write against a single shared file |
| pre-existing compose content -> `ProxyConfig` rows (adoption path) | file content the user (not Docktor) authored becomes database state |

## STRIDE Threat Register (ASVS L1, blocking on `high`)

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-08 | Spoofing | `DELETE /api/proxy-configs/:id` | high | mitigate | the plugin-level `requireAuth` hook from 06-01 covers every route in the file including the new DELETE; the integration test asserts 401 without a session cookie |
| T-06-09 | Tampering | interleaved compose read-modify-write | high | mitigate | `withKeyedLock(stackId, ...)` serializes every proxy compose mutation for one stack; the held-out concurrency test is required to go red with the lock removed before it is accepted |
| T-06-10 | Tampering | adoption path parsing user-authored `VIRTUAL_HOST` | medium | mitigate | adopted domain strings are re-validated against the same `hostnamePattern` from `@docktor/shared` before a row is created; an entry that fails validation is skipped with a warning, never written back into the file |
| T-06-11 | Denial of Service | unbounded growth of the keyed-mutex map | low | mitigate | the entry for a key is deleted in a `finally` when the stored tail is still the one that call appended |
| T-06-12 | Repudiation | a removal that deletes the row but fails the compose write | medium | accept | the redeploy is the last step and its failure surfaces through `deployStack`'s existing ERROR transition and status log; the row is already gone, which matches the user's stated intent — reintroducing it would be a worse surprise than a failed redeploy the status log already records |
</threat_model>
